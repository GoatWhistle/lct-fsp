# Механики подбора и тестирования

Что система делает, по каким формулам и почему именно так. Значения по умолчанию и имена
параметров конфига — в [parameters.md](parameters.md): здесь параметр назван по имени, а число
приведено, только когда без него непонятна мысль. Термины — [glossary.md](glossary.md), угрозы —
[threat-model.md](threat-model.md), проверка качества — [validation-plan.md](validation-plan.md).

## 1. Сквозная логика

**Кандидат.** Опрос → направление, то есть специализация. Сам выбирает грейд → адаптивный тест
на этот грейд → **оценка теста** → **категория** (специализация × грейд) по правилу уверенности.
Параллельно копится **профиль навыков**: уровень и погрешность по каждой теме, сведённые из всех
сигналов с весами уровней доверия.

**Работодатель.** Потребность → требования по темам → подборка: категория отсекает, внутри
порядок по P(соответствия) × P(принятия) с объяснением из самой формулы скора → приглашение с
вилкой из недельного бюджета → кандидат принимает → контакты и полный профиль раскрываются.

**Главный принцип.** Сигнал весит тем больше, чем труднее его подделать:

| Уровень доверия | Сигнал | Куда входит |
|---|---|---|
| 1 | Результаты ФСП — очные соревнования под надзором | профиль |
| 2 | Проверочный блок — короткий, на время, из невиданных семейств | категория и профиль |
| 3 | Адаптивный тест без надзора | категория и профиль |
| 4 | Регулярные задания от работодателей, оценка по рубрике | профиль |
| 5 | Самоописание — только стек | отдельное слагаемое скора с потолком |

Категорию определяет только тест (уровни 2–3): это ворота выдачи, и для всех они должны
измеряться одной сопоставимой процедурой. ФСП — самый весомый сигнал в профиле и ранжировании,
но на категорию не влияет, поэтому кандидат без ФСП ничего не теряет на входе в выдачу.

## 2. Справочники и шкала уровня

- **Справочники — данные, а не код:** специализации (MVP: бэкенд, фронтенд, данные/ML, QA,
  DevOps), грейды (стажёр, junior, middle, senior), темы каждой специализации, технологии стека
  со связью «технология → темы», сферы бизнеса. Новая специализация добавляется данными.
- **«Отрасль» из ТЗ — это специализация**, IT-направление; так её понимают и организаторы. Сферы
  бизнеса — финтех, госсектор, ритейл — отдельный справочник: сфера деятельности компании и
  необязательные интересные сферы кандидата. Их совпадение — признак P(принятия) (§13), на
  категорию и профиль навыков сфера не влияет.
- У темы в специализации есть вес $w_t$, $\sum_t w_t = 1$, по умолчанию равный. Он задаёт общий
  уровень (§3) и бланк теста (§6).
- **Шкала θ** — логиты IRT, общая для всех тем специализации. Грейду соответствует порог $c_g$
  (`grade_thresholds`: стажёр −1,5, junior −0,5, middle 0,5, senior 1,5): полосы грейдов шириной 1.
- **Экспертная сложность.** Эксперт относит семейство заданий к грейду, в середине полосы
  которого кандидат решает его в половине случаев: стартовая сложность $b_0$ — середина полосы
  (`expert_difficulty_by_grade`), стартовая разделяющая сила $a_0$ — `expert_discrimination`.
- Шкала не плывёт при калибровке: её держат якорные семейства с замороженными параметрами (§7).

## 3. Модель навыка — IRT 2PL

Вероятность верного ответа кандидата с уровнем $\theta_t$ по теме $t$ на семейство $f$:

$$P(u = 1 \mid \theta_t) = \sigma\big(a_f(\theta_t - b_f)\big), \qquad \sigma(x) = \frac{1}{1 + e^{-x}}$$

$b_f$ — сложность, $a_f$ — разделяющая сила; оба принадлежат семейству, а не экземпляру.

**Почему 2PL.** Модель Раша (1PL) считает все задания одинаково разделяющими, а «что выведет
код» и выбор из вариантов разделяют по-разному. 3PL добавляет параметр угадывания, который
плохо оценивается на сотнях ответов; угадывание гасим форматом: вычисляемый ответ или выбор с
перемешиванием из пяти и более вариантов.

**Иерархическое априорное.** Уровень по теме — общая часть плюс отклонение темы:

$$\theta_t = \theta_s + \delta_t, \qquad \theta_s \sim N(0, s_\theta^2), \qquad \delta_t \sim N(0, s_\delta^2)$$

$s_\theta$ — `theta_prior_sd`, $s_\delta$ — `topic_deviation_sd`.

На тему в тесте приходится 3–5 заданий. С независимым априорным по каждой теме оценки сильного
кандидата стягивались бы к нулю, то есть к junior, и senior не набирал бы уверенности. Общая
часть $\theta_s$ даёт темам занимать силу друг у друга: ответы по SQL кое-что говорят и о
бэкенде в целом.

**Обновление.** Совместное апостериорное $(\theta_s, \delta_1, \dots, \delta_T)$ приближается
нормальным $N(\mu, \Sigma)$ (приближение Лапласа). Наблюдения учитываются по порядку времени;
наблюдение $u$ по теме $t$ с весом $w$ сдвигает оценку так:

$$h = e_s + e_t, \quad p = \sigma\big(a(h^\top\mu - b)\big), \quad I = a^2 p(1-p)$$

$$\Sigma' = \Sigma - \frac{wI\,\Sigma h h^\top \Sigma}{1 + wI\,h^\top\Sigma h}, \qquad \mu' = \mu + w\,a\,(u - p)\,\Sigma' h$$

Это шаг Ньютона к моде, как в рейтинге Глико; для наблюдений с большой разделяющей силой
(достижения ФСП) шаг повторяется до сходимости моды. $w$ — вес уровня доверия: в оценке теста
$w = 1$, в профиле — по §11.

**Уровень по теме** — $\theta_t \sim N(h^\top\mu,\ h^\top\Sigma h)$: это «уровень и
погрешность» в профиле. **Общий уровень** по специализации — среднее по темам с весами
справочника:

$$\bar\theta = \sum_t w_t \theta_t \sim N(g^\top\mu,\ g^\top\Sigma g), \qquad g = e_s + \sum_t w_t e_t$$

Грейд решается по $\bar\theta$, а не по $\theta_s$ и не по правилу «каждая тема выше порога».
$\theta_s$ — уровень гипотетической «средней темы», и его погрешность упирается в предел при
любом числе заданий. Правило «каждая тема» превратило бы одну слабую тему в провал грейда и
удлинило тест. Специфику тем учитывает подбор: потребность сама говорит, какие темы важны (§12).

**Поправка погрешности.** Модель занижает погрешность: на симуляции с известной истиной
фактическая ошибка общего уровня на остановке теста больше $\bar\sigma$ в 1,1–1,2 раза —
$\mathrm{sd}(z) \approx 1{,}1\text{–}1{,}2$, $z = (\hat{\bar\theta} - \bar\theta^*)/\bar\sigma$, при
идеале 1, — даже когда оценке известны истинные параметры семейств. Это свойство оценщика:
приближение Лапласа с одним шагом на наблюдение, а адаптивный выбор берёт задания, самые
информативные при текущей оценке, и информация при оценке выходит больше, чем при истинном уровне.
Поэтому погрешность уровня — $\kappa\sigma$, $\kappa$ — `level_sd_inflation`:

$$\theta_t \sim N\big(h^\top\mu,\ \kappa^2 h^\top\Sigma h\big), \qquad \bar\theta \sim N\big(g^\top\mu,\ \kappa^2 g^\top\Sigma g\big)$$

Поправка действует везде, где нужна погрешность уровня: остановка теста (§6), правило уверенности
(§4), профиль навыков (§11), калибровка (§7). Среднее и шаг обновления она не меняет: шаг идёт по
$\Sigma$ модели. Без поправки правило уверенности срабатывает раньше, чем должно: на симуляции грейд
выше истинного получали в среднем 4 % определений, с поправкой — 2 %.

$\kappa$ подбирается на настроечном наборе плана валидации по его правилу, проверка —
$\mathrm{sd}(z)$ на основном наборе в пределах 0,9–1,1 по каждой специализации. Неточность
параметров семейств в погрешность почти не входит: их ошибки независимы между семействами и за
два десятка заданий усредняются, а учёт дисперсии параметров в оценке меняет $\mathrm{sd}(z)$ лишь
на 0,01–0,03. Вес наблюдений $1/\kappa^2$ дал бы ту же погрешность, но стянул бы и среднее к
априорному; итерации до моды вместо одного шага снижают $\mathrm{sd}(z)$ лишь на 0,02–0,04.

**Оценка — чистая функция:** (априорное, упорядоченные наблюдения, момент запроса) →
$(\mu, \Sigma)$. Без БД и состояния, детерминирована, покрывается юнит-тестами и проверками свойств:
больше верных ответов — выше уровень, больше заданий — меньше погрешность.

## 4. Категория и правило уверенности

Категория — специализация из опроса × грейд из теста. Грейд $g$ присваивается, когда

$$P(\bar\theta \ge c_g) = \Phi\!\left(\frac{\bar\mu - c_g}{\bar\sigma}\right) \ge \gamma$$

где $\gamma$ — порог уверенности `grade_confidence` (по умолчанию 0,8), а $\bar\mu, \bar\sigma$ —
по **оценке теста**: только наблюдения теста и проверочного блока, $w = 1$; $\bar\sigma$ — с
поправкой погрешности (§3).

**Почему уверенность, а не процент верных.** Процент зависит от того, какие задания достались: в
адаптивном тесте и сильный, и слабый решают примерно половину своих заданий. Правило уверенности
ограничивает завышение: присваивая грейд, система допускает не больше 20 % вероятности по модели,
что кандидат ниже порога. Это верно, только пока погрешность честная, — отсюда поправка (§3).
Цена — занижение у тех, кто у нижней границы полосы; они видят «между junior и middle» и могут
пересдать.

**Первичное определение — каскад вниз.** Тест на заявленный грейд $g$. Если правило не
выполнено, сразу предлагается $g-1$. Дотест продолжает ту же оценку: прошлые ответы — наблюдения
того же уровня. Если уверенность для $g-1$ уже набрана, грейд присваивается без дотеста. Не
прошёл стажёра — кандидат остаётся без категории, повтор через `no_category_retest_days`. Каскад
— одно определение, интервал смены грейда на него не действует.

**Смена грейда вверх.** Попытка на грейд выше — отдельное измерение с чистого листа: априорное
без прошлых попыток, чтобы категория каждого кандидата опиралась на одну сопоставимую процедуру
(профиль при этом копит все попытки). Категория меняется, только если правило выполнено;
проваленная попытка категорию не меняет, принудительного понижения нет.

**Переход вниз** — без теста: правило уверенности для младшего грейда уже выполнено той же
оценкой, $P(\bar\theta \ge c_{g-1}) \ge P(\bar\theta \ge c_g) \ge \gamma$. Категория по-прежнему
определена тестом, а переход не показывает ни одного задания и не тратит банк.

**Правило ожидания.** Грейд не должен скакать — сегодня junior, завтра senior, послезавтра
middle, — но провал не должен сжигать попытку:

- **Часы сдвигает только смена.** Попытка вверх — не раньше `grade_change_interval_days` после
  последней смены категории, вверх или вниз. Первое определение сменой не считается: кто сразу
  прошёл заявленный грейд, может сразу попробовать выше — это и предлагает подсказка ниже.
- **Провал — короткий интервал.** Попытка на грейд, который не дался, или выше — не раньше
  `grade_retry_interval_days` после проваленной попытки. Не дался и заявленный грейд первичного
  определения, если каскад увёл ниже. Попытку на грейд ниже проваленного короткий интервал не
  держит. Интервал нужен не как наказание: без него повторы превращаются в лотерею «рано или поздно
  повезёт» — у кандидата чуть ниже порога каждая попытка даёт новый шанс пройти случайно, — и в
  сбор банка заданий. Организаторы называют срок «раз в месяц», отсюда значение.
- **Вниз — без ожидания.** Переход вниз не показывает заданий, ждать незачем. Обратный путь
  наверх — тестом по общему правилу, через `grade_change_interval_days`.

Кандидат видит дату, когда попытка вверх станет доступна; раньше неё бэкенд попытку не начинает.

**Подсказка «попробуйте грейд выше»** — когда $P(\bar\theta \ge c_{g+1}) \ge$
`grade_up_hint_confidence`.

**Язык уверенности.** Вероятности полос $\pi_g = P(c_g \le \bar\theta < c_{g+1})$: «уверенно
middle», если $\pi_g \ge \gamma$ (тот же порог уверенности); иначе «между junior и middle» — два
соседних грейда с наибольшей суммой. Категория и словесный уровень могут различаться: «категория
middle, уровень между middle и senior» — честное описание кандидата у верхней границы.

## 5. Семейства заданий

**Семейство** — шаблон, генератор параметров и проверка ответа кодом. **Экземпляр** — шаблон с
конкретными параметрами; seed экземпляра хранится в предъявлении, экземпляр воспроизводим.

Форматы ответа:

- **вычисляемый ответ** — что выведет код, результат SQL-запроса, состояние после трассировки;
  кандидат вводит его строкой;
- **выбор** — ответ — буква одного из вариантов; неверные варианты — типичные ошибки;
- **перестановка** — ответ — буквы всех вариантов в верном порядке строкой («KBXF»); фронт
  показывает варианты с буквами и поле ввода;
- **короткая задача с автопроверкой** — функция, которую проверяют тесты.

В выборе и перестановке тексты вариантов перемешиваются из seed экземпляра, а буквы — случайные
буквы латиницы, по алфавиту. С буквами A, B, C по порядку верный ответ одного экземпляра проходил
бы на другом с вероятностью 1/k — при четырёх вариантах это 0,25, впятеро выше
`family_answer_collision_max`. Со случайными буквами буква верного варианта совпадает с
вероятностью 1/26. Проверка ответа не смотрит на регистр, пробелы и разделители между буквами
(«k, b - x f» — то же, что «KBXF») и читает кириллические двойники латинских букв латиницей.
Угадывание внутри экземпляра остаётся 1/k: модель 2PL его не учитывает, поэтому выбор — для
сценариев, где варианты — реальные решения с компромиссами, а не для проверки знания фактов.
Случайные буквы защищают от утёкшей буквы, но не от утёкшего правила: «фантомное чтение —
REPEATABLE READ» подходит к каждому экземпляру с этой аномалией. Такое правило — само проверяемое
умение, а не ответ одного экземпляра, поэтому сценарное семейство держится числом разных
ситуаций в генераторе, а утечку на нём ловит детектор дрейфа (§8), как на любом другом.

**Вид задания** у каждого семейства — что оно проверяет: `trace` — что выведет код или запрос,
`compute` — посчитать по данным, и сценарные `scenario_choice` — выбор решения с компромиссами,
`bug_hunt` — поиск ошибки, `ordering` — порядок шагов, `incident` — разбор инцидента. Вид —
свойство генератора и размечается по чтению его условия.

**Почему потолок трассировки и сценарии у старших грейдов.** Задание «что выведет код: сумма по
срезу списка» решат и junior, и senior — оно мерит внимательность, а не грейд. Тема, собранная из
трассировки, разделяет кандидатов по аккуратности счёта в уме, и жюри, пройдя тест за людей
разного уровня, этого не узнает в своих ответах. Поэтому доля `trace` среди семейств темы не выше
`bank_max_trace_share_per_topic`, а в ячейках middle и senior каждой темы не меньше
`bank_min_scenario_families_per_grade` сценарных семейств: решения, которые отличают старший грейд,
— выбор под нагрузку и цену, порядок безопасной выкатки, разбор инцидента.

**Матрица грейдов** — содержательная опора банка: для каждой ячейки «тема × грейд» — наблюдаемые
умения, что человек делает, а не сколько лет стажа. Данные — `backend/config/grade_matrix.yaml`,
документ для жюри [grade-matrix.md](grade-matrix.md) генерируется из них. Ячейка с семействами без
описания в матрице — неясно, что мерят её задания; описанная ячейка без семейств — умения, которые
тест не проверяет.

**Отчёт покрытия** — одна команда (`uv run python -m bank_report` из `backend/`): доля трассировки
по темам против потолка, сценарные семейства в ячейках middle и senior против минимума, ячейки
без семейств и без описания, семейства с пометкой сверки сложности (§7), когда есть данные
калибровки. Отчёт ничего не роняет; строгие тесты порогов на настоящем банке включаются,
когда банк наполнен, и зовут те же проверки.

Требования к семейству при попадании в банк:

1. Эталон вычисляется исполнением кода, а не хранится текстом; ответ проверяет бэкенд,
   правильные ответы на фронт не уходят.
2. Верные ответы двух случайных экземпляров совпадают с вероятностью не выше
   `family_answer_collision_max`: утёкший ответ не подходит к чужому экземпляру.
3. **Однородность:** разброс сложности по группам параметров не выше
   `family_instance_difficulty_sd_max`, иначе семейство делится (например, «с рекурсией» и «без»).
   Так экземпляры одного семейства сопоставимы по сложности, и это проверяется данными — по
   остаткам модели в группах параметров.
4. В банке не меньше `bank_min_families_per_topic` семейств на тему и не меньше
   `bank_min_families_per_grade` на каждый грейд темы, из них `anchor_families_per_topic` якорных.
   Без заданий нужной трудности тест не набирает точности у краёв шкалы и упирается в лимит
   заданий.

**LLM — только офлайн для черновиков шаблонов.** В банк шаблон попадает после ревью человеком и
автопроверки: генератор, эталон, коллизии ответов. Задания под каждого кандидата LLM не
генерирует: сложность одноразового задания неизвестна, и калибровать его не на чем. Параметры
семейства оцениваются на всех его экземплярах.

## 6. Адаптивный тест

**Бланк** — веса тем и ограничения покрытия. Для теста на категорию веса — $w_t$ специализации;
для превью теста по вакансии — веса тем потребности (§12), движок тот же. Каждая тема получает
не меньше `test_min_items_per_topic` заданий и не больше доли `test_max_topic_share` от длины.

**Старт.** Задания выбираются по той же чистой функции оценки, но с априорным средним в пороге
заявленного грейда: тест сразу начинается с заданий нужного уровня. Сама оценка, по которой
решается грейд, считается с общим априорным. Заявленный грейд влияет только на выбор заданий и
никогда на оценку — иначе заявивший senior получал бы фору.

**Шаг.**

1. **Тема.** Сначала недобранные минимумы покрытия. Иначе — тема с наибольшим вкладом в
   погрешность общего уровня $w_t^2\sigma_t^2$ среди тем, не упёршихся в потолок доли.
2. **Кандидаты:** семейства темы, кроме скомпрометированных, превысивших потолок показов и
   показанных в текущей попытке. Семейства, виденные кандидатом в прошлых попытках и блоках,
   берутся, только когда невиданных в теме не осталось, — давно виденные первыми; экземпляр всегда
   новый.
3. **Информация** при текущей оценке темы: $I_f(\mu_t) = a_f^2\,p(1-p)$.
4. **Случайный выбор** из `exposure_top_k` самых информативных — каждый получает свой набор. Пул
   не шире `bank_min_families_per_grade`: на грейд темы в банке по 2–3 семейства, и пул пошире
   всегда захватывает соседний грейд — задания мимо уровня, на которых тест теряет почти весь
   выигрыш адаптивности. С ростом банка пул можно расширить.
5. **Новый экземпляр** со свежим seed.

**Порядок тем от резюме и самоописания не зависит.** Тему выбирают только минимумы покрытия и
$w_t^2\sigma_t^2$ по ответам этой попытки. Если бы резюме подсказывало темы, кандидат вписал бы
в него свои сильные темы, и тест набрал бы по ним задания до остановки по погрешности: общий
уровень поднялся бы за счёт выбора тем, а не умения. Поэтому подсказки тем по резюме нет.

**Потолок показов.** Доля попыток за окно показов, в которых показано семейство, не выше
`exposure_max_rate`. Окно показов — последние `exposure_window_attempts` попыток по
специализации, где было хотя бы одно предъявление, включая идущие: задание раскрыто показом,
а не остановкой попытки. Если в теме под
потолком ничего не осталось, берётся наименее показанное семейство, событие пишется в лог — это
сигнал, что банк темы мал. В первых попытках по специализации окно почти пусто и под потолком
почти ничего нет — там запасной выбор обычен, а при пустом окне пишется в лог как обычное
событие. Потолок осмыслен, только когда семейств хватает: средняя доля показов
— примерно $n_t / N_t$ (заданий темы в тесте на семейства темы в банке). При четырёх заданиях
темы на тест и десяти семействах средняя доля 0,4, и потолок 0,5 срезает только «любимчиков».
Главный рычаг — рост банка: при двадцати семействах на тему потолок можно опустить до 0,25.

**Остановка:** $\bar\sigma \le$ `test_stop_sd`, задано не меньше `test_min_items` и выполнены
минимумы покрытия — либо достигнут `test_max_items`. Остановка по точности уравнивает точность,
а не длину: сильный и слабый кандидат заканчивают с одинаковой погрешностью.

$\bar\sigma$ здесь — с поправкой погрешности (§3). Порог 0,40 держит медиану около 20 заданий.
При пороге 0,35 с честной погрешностью на прогретом банке в четырёх специализациях из пяти больше
половины тестов упираются в лимит заданий, а сверх потолка показов берётся до половины заданий:
при 11–17 семействах на тему тест в 30 заданий видит до половины темы. Прежние 0,35 без поправки
на деле означали ошибку на финише около 0,44, нынешние 0,40 — честные.

**Дотест каскада** (§4) — та же процедура: минимум заданий и минимумы покрытия считаются внутри
дотеста, а $\bar\sigma$ — по всей оценке определения. Длина адаптивного теста заранее неизвестна,
кандидат видит «задание N, не больше `test_max_items`».

**Восстановление.** Состояние попытки — список предъявлений, оценка — чистая функция от него:
прерванная попытка восстанавливается пересчётом после перезапуска бэкенда.

**Предъявление хранится целиком:** попытка, семейство, seed и параметры экземпляра, ответ,
верность, время ответа по часам сервера (клиентские часы подделываются), оценка темы до ответа
$(\mu_t, \sigma_t)$, события вставки и потери фокуса, если кандидат дал согласие. На этих записях
стоят калибровка, защита теста и валидация.

**Блок по теме** — короткий адаптивный тест по одной теме специализации категории. Это действие
из подсказок «что поднимет выше» (§15); без категории блока нет.

- **Длина фиксированная** — ровно `topic_block_items` заданий, без остановки по погрешности: блок
  не определяет уровень, а добавляет наблюдения. Раньше он кончается, только если у темы не
  осталось невиданных в блоке семейств в выдаче.
- **Выбор** — тот же шаг, что в тесте: информация при текущей оценке темы, случайный выбор из
  top-k, потолок показов, запрет повтора семейства в блоке и давно виденные после невиданных.
  Кандидаты — только семейства темы, ограничения покрытия бланка не применяются. Оценка для выбора
  и оценка темы до ответа в предъявлении — оценка теста по всем ответам кандидата по специализации
  с весом 1, без сдвига к порогу грейда.
- **Ответ — обычное предъявление:** хранится целиком, шаг Эло и учёт показов идут по нему, после
  остановки — итоговые оценки темы без каждого ответа для переоценки. В профиль ответы входят с
  весом `trust_weight_test`, профиль пересчитывается тем же путём, что после теста.
- **Путь не меняется:** категория, грейд, журнал смен, часы ожидания смены грейда, дата повтора,
  шаг и история пути считаются только по попыткам определения и попыткам вверх.
- **Не чаще `topic_block_interval_days` на тему**, считая от старта последнего блока по этой
  теме. Брошенный блок тоже считается — иначе блок можно бросать до удобных заданий. Другие темы
  интервал не держит.
- **Одна незавершённая попытка на кандидата:** пока идёт блок, тест на грейд выше не начинается,
  и наоборот. Прерванный блок продолжается с того же задания, как прерванная попытка.

## 7. Калибровка по Эло

**Старт** — экспертные $a_0$, $b_0$. **После каждого ответа** кандидат «играет» против
семейства, сложность обновляется онлайн:

$$p = \sigma\!\left(\frac{a_f(\mu_t - b_f)}{\sqrt{1 + \pi a_f^2 \sigma_t^2 / 8}}\right), \qquad b_f \leftarrow b_f - K_n\,(u - p)$$

$$K_n = \max\!\left(K_{\min},\ K_0\,\frac{n_0}{n_0 + n}\right)$$

$K_0$ — `elo_k_initial`, $K_{\min}$ — `elo_k_min`, $n_0$ — `elo_k_half_responses`, $n$ — число
ответов на семейство, $(\mu_t, \sigma_t)$ — оценка кандидата по теме до ответа, переведённая
связкой шкалы (ниже).
Знаменатель внутри $\sigma$ учитывает погрешность кандидата, как в Глико: ответ кандидата с
неточной оценкой двигает сложность меньше. Перевод в IRT прямой: шкала Эло здесь — сразу логиты
θ, и $b_f$ — та же сложность 2PL.

**Калибровка отдельно от ответа.** Шаг Эло, пересчёт связок и пакетная переоценка идут после
фиксации ответа кандидата, отдельным шагом: сбой калибровки ответ не отменяет. Поэтому следующий
выбор задания может видеть сложность на один шаг Эло старше.

**Разделяющая сила** онлайн не обновляется: слишком шумно. Когда у семейства набирается
`calibration_refit_min_responses` ответов, $(a_f, b_f)$ переоцениваются пакетно — логистической
регрессией ответов на итоговые оценки кандидатов со штрафом к экспертным значениям
(`calibration_refit_difficulty_prior_sd`, `calibration_refit_log_discrimination_prior_sd`).
Итоговая оценка темы берётся без самого ответа — иначе верный ответ поднимает уровень, с которым
его сравнивают, и разделяющая сила завышается, — и переводится связкой шкалы. Штраф на
разделяющую силу строже, чем на сложность: адаптивный выбор берёт самые информативные семейства,
то есть те, у которых переоценка завысила $a$, и шум оценки $\hat a$ превращается в
систематически заниженную погрешность уровня (van der Linden, Glas, 2000).

**Якорные семейства** — по `anchor_families_per_topic` на тему с замороженными параметрами. Они
держат начало и масштаб шкалы. Без якорей совместная калибровка кандидатов и заданий может
уплыть целиком, и пороги грейдов потеряют смысл.

**Связка шкалы.** Оценка теста стягивается к априорному среднему, и если популяция шире
априорного, уровни пережаты к центру. Калибровка, которая принимает пережатые уровни за точные,
сжимает сложности к центру и завышает разделяющую силу; следующий тест на таких параметрах
пережимает уровни сильнее, и шкала стягивается сама, а погрешность уровня занижается — правило
уверенности перестаёт ограничивать завышение. Поэтому уровень, с которым калибровка сравнивает
ответ, сначала переводится связкой

$$\theta \approx \alpha + \beta\mu, \qquad \text{погрешность}\ \sqrt{\beta}\,\sigma$$

(пережатие в $\beta$ раз сжимает и среднее, и дисперсию). $(\alpha, \beta)$ — максимум
правдоподобия ответов на якорные семейства: их параметры известны, и по ним видно, как оценки
теста соотносятся со шкалой, — та же идея, что связка шкал по общим заданиям (Kolen, Brennan,
2014). Так якоря держат начало ($\alpha$) и масштаб ($\beta$). Связок две — по оценкам до ответа
для Эло и по итоговым оценкам без ответа для переоценки. Обе пересчитываются при остановке
попытки по ответам на якоря из окна связки — последних `calibration_link_window_attempts`
остановленных попыток специализации: итоговая оценка без ответа есть только у остановленной; пока таких ответов меньше `calibration_refit_min_responses`, связка тождественная.
Тождественная она и тогда, когда ответы на якоря не дают $\beta > 0$, то есть не связаны с оценками
или противоречат им: при $\beta \le 0$ у модели нет погрешности $\sqrt{\beta}\,\sigma$.

**Опорные параметры для детектора дрейфа** — результат первой пакетной переоценки, после
`calibration_refit_min_responses` ответов; до неё семейство на разогреве, и детектор по нему не
работает. Они же — текущие: после переоценки Эло сложность не двигает. Эло сравнивает ответ с
оценкой до ответа, а в начале теста она стянута к априорному, поэтому равновесие Эло смещено: на
симуляции семейства стажёра выходили в среднем тяжелее истинных на 0,16–0,25. Смещение одно для
всех заданий уровня и внутри теста кандидата не усредняется — погрешность уровня занижается.
Переоценка сравнивает ответ с итоговой оценкой без него и такого смещения не несёт: при 500
ответах на семейство в среднем ошибка сложности — 0,17–0,20 против 0,24–0,27, когда Эло
продолжает после переоценки. Дрейф (§8) меряется от опорных — иначе калибровка «съела» бы утечку,
приняв её за то, что семейство просто легче. Утечка во время разогрева попала бы в сами опорные
параметры, поэтому при заморозке опорная сложность сверяется с экспертной: если семейство
оказалось легче экспертной оценки больше чем на `calibration_expert_gap_review`, оно выводится из
выдачи до ручной проверки — это либо утечка, либо ошибка эксперта. Сверка идёт и в другую
сторону: семейство тяжелее экспертной больше чем на ту же величину — эксперт недооценил задание
или формулировка сбивает. Такое семейство кандидату не подыгрывает, поэтому из выдачи не
выводится, а только помечается и попадает в отчёт покрытия (§5): его грейд в банке, возможно,
надо поднять.

**Согласие семейства с моделью.** Переоценка подбирает $a_f, b_f$, но не проверяет, что семейство
вообще ведёт себя по 2PL. Ошибка в эталоне, двусмысленная формулировка, ответ, который угадывается
по форме, дают кривую ответа не той формы при любых параметрах, и такое семейство тихо портит
оценки всех, кому досталось. Дрейф ловит сдвиг — семейство стало легче; согласие ловит форму.

После каждой пакетной переоценки проверка ищет у семейства форму, которую 2PL приближает другими
$(a, b)$ и которую поэтому не видно в расхождении с только что подобранной кривой. Ответы — те же,
что у переоценки: итоговая оценка темы без ответа, переведённая связкой. Семейство выводится, если
сработала любая из двух частей.

- **Разделяющая сила.** Переоценённая $\hat a_f <$ `item_fit_discrimination_min` — семейство не
  различает уровни, что бы ни было причиной. Ответ, не зависящий от уровня, — это 2PL с $a \to 0$;
  дальше переоценку не пускает только штраф на $\ln a$, и $\hat a$ такого семейства на 200 ответах
  около 0,5–0,6.
- **Модель с потолком.** $P = d \cdot p_i(a, b)$, где $p_i$ — вероятность верного с поправкой на
  погрешность уровня, как в шаге Эло. Для каждого $d$ от `item_fit_ceiling_min` до единицы с шагом
  `item_fit_ceiling_step` подбираются $(a, b)$ тем же скорингом Фишера с теми же штрафами, что у
  переоценки. Семейство выводится, если перевес $G_f >$ `item_fit_ceiling_gain_max`:

$$G_f = \max_d \ell_f(d, \hat a_d, \hat b_d) - \ell_f(1, \hat a_f, \hat b_f), \qquad \ell_f = \sum_i \ln P(u_i) - \frac{(b - b_0)^2}{2\sigma_b^2} - \frac{(\ln a - \ln a_0)^2}{2\sigma_{\ln a}^2}$$

$G_f$ — на сколько нат модель с потолком объясняет ответы лучше переоценённой 2PL; $G_f \ge 0$,
потому что среди потолков есть единица. Переоценка не может спрятать порчу от этой части: у
альтернативы та же свобода, что у неё, плюс потолок. Неверный эталон у половины экземпляров —
ровно потолок ½. Ответ, не зависящий от уровня, — потолок около ½ при $b \to -\infty$ без штрафа на
$a$, тогда как 2PL платит за $a \to 0$ штрафом. Граница $\hat a$ добирает плоские семейства, у
которых перевес на 200 ответах ещё мал.

Семейство, не прошедшее проверку, выводится из выдачи до ручной проверки, банк получает задачу на
правку или замену — запись в журнал с кодом семейства и причиной. Ответы на него в незавершённых
попытках остаются в оценке: такое семейство несёт меньше информации, чем обещает модель, но не
подыгрывает кандидату, а выбрасывание ответов удлинило бы тест. Уже присвоенные категории не
пересматриваются.

**Якорь** не переоценивается, его $(a, b)$ фиксированы, и подогнать под ответы их нельзя — с ними
сверяется RMSD. При пересчёте связки ответы на якорь делятся на `item_fit_groups` групп равного
размера по уровню, в группе $k$ — наблюдённая доля верных $O_k$ и ожидаемая $E_k$:

$$E_k = \frac{1}{n_k}\sum_{i \in k} p_i, \qquad V_k = \frac{1}{n_k^2}\sum_{i \in k} p_i(1 - p_i), \qquad \mathrm{RMSD}_f = \sqrt{\frac{\max\!\left(0,\ \sum_k n_k\,\big[(O_k - E_k)^2 - V_k\big]\right)}{\sum_k n_k}}$$

$V_k$ — дисперсия доли верных у семейства, которое ведёт себя ровно по модели: без её вычета на
сотнях ответов шум выборки сам даёт RMSD около порога. Якорь с $\mathrm{RMSD}_f >$
`item_fit_rmsd_max` выводится из выдачи и до проверки не входит в связку шкалы. Порог 0,12 — как у
похожей меры в PISA (OECD, 2017). Критерий χ² на сотнях ответов отмечает и несущественные
отклонения, а S-X² (Orlando, Thissen, 2000) стоит на суммарном балле, которого в адаптивном тесте
нет.

**Почему так.** Проверка выбрана на D3 из пяти гипотез по правилу плана валидации, записанному до
прогона (команда стенда `fit`). RMSD против переоценённых $(a, b)$ — прежняя проверка у всех
семейств — порчу почти не видела: на D3 TPR 0 по ошибке эталона и 0,09 по плоским. Переоценка её
поглощает: плоское семейство уходит в $\hat a \approx 0{,}6$, ошибка эталона — в 2PL тяжелее на
1,5–2 логита и с $a$ ниже на треть, и на диапазоне отвечавших кривая совпадает с данными.
Отвергнуты: RMSD против экспертной формы ($a = a_0$) — ошибка эталона прячется в сдвиге $b$, TPR
0,43; одна граница $\hat a$ — ловит только плоские; недобор доли верных в верхней группе против
экспертной формы — 0,76 при FPR 0,04; одна модель с потолком — 0,79 по плоским. Сравнение по
экземплярам не проверялось: экземпляр строится из своего seed, повторов почти нет. Выбранное
сочетание на D3 — TPR 0,90 по ошибке эталона и 0,91 по плоским при FPR 0,03.

Ограничения. Пологую исправную кривую модель с потолком отчасти имитирует: из семейств с
$\ln a^* = \ln a_0 - 0{,}6$ (край разброса D1) на 200 ответах выводится около трети, с
$\ln a_0 + 0{,}6$ — ни одно. Испорченные семейства после первых ответов адаптивный выбор берёт
редко — Эло уводит их сложность вверх, после переоценки низкая $\hat a$ мало информативна, — и
часть из них не набирает ответов на переоценку: проверка их не видит, но и в тесты они почти не
попадают. Что из этого ловится на основном наборе, показывает M21.

**Почему Эло:** онлайн, O(1) на ответ, работает с первого ответа, без пакетного переобучения;
проверенный подход адаптивных обучающих систем (Pelánek, 2016).

## 8. Защита теста

**Детектор дрейфа** — risk-adjusted Bernoulli CUSUM (Steiner и др., 2000) по каждому семейству.
На каждый ответ:

$$p_0 = \sigma\!\left(\frac{a(\hat\theta - b)}{\sqrt{1 + \pi a^2 \hat\sigma^2 / 8}}\right), \quad p_1 = \sigma\!\left(\frac{a(\hat\theta - b + \Delta)}{\sqrt{1 + \pi a^2 \hat\sigma^2 / 8}}\right), \quad W = \begin{cases}\ln(p_1/p_0), & u = 1\\ \ln\big((1-p_1)/(1-p_0)\big), & u = 0\end{cases}$$

$$S \leftarrow \max(0,\ S + W)$$

Когда $S$ превышает `drift_cusum_h`, семейство помечается скомпрометированным. $a, b$ — опорные
параметры, $\hat\theta$ — оценка кандидата по теме до ответа, переведённая связкой шкалы по
оценкам до ответа — той же, что у шага Эло (§7), $\Delta$ —
`drift_shift`: насколько легче становится слитое семейство. Поправка на уровень отвечавших
встроена: семейство, которое чаще решают просто более сильные кандидаты, тревоги не поднимает. Знаменатель — погрешность оценки $\hat\sigma$, как в шаге Эло (§7): в начале теста оценка
стянута к априорному, а задание уже выбрано под заявленный грейд, и без поправки верные ответы
сильных честных кандидатов на трудных заданиях копили бы ложную тревогу. На стенде вариант без
поправки давал втрое больше ложных тревог при том же пороге.
Скомпрометированное семейство выводится из выдачи, банк получает задачу на замену, ответы на него
в незавершённых попытках выпадают из оценки — у определения с каскадом во всех его звеньях, — а
после остановки помечаются выпавшими и в профиль не входят. Уже присвоенные категории
автоматически не пересматриваются. Скомпрометированный якорь не входит и в связку шкалы. Детектор
идёт после фиксации ответа отдельным шагом, как калибровка: ответ кандидата его не ждёт, и
следующее задание может прийти из семейства, помеченного только что.

**Модель времени ответа** — логнормальная (van der Linden, 2006). По семейству $\ln T$ верных
ответов $\sim N(m_f, s_f^2)$, оценка робастная (медиана, MAD), после `rt_min_responses` верных
ответов. Флаг предъявления: ответ верный, задание трудное для кандидата ($p \le$ `rt_hard_item_p` по
оценке до ответа) и $(\ln T - m_f)/s_f \le -$`rt_fast_z`. Время — по серверу.

Время в оценку уровня не входит, только в сигнал подозрения. Скорость — не навык: медленный верный
ответ — тот же верный ответ, а совместная модель уровня и скорости штрафовала бы аккуратных и тех,
кому неудобен интерфейс.

**Согласие попытки с моделью.** Флаги времени ловят быстрый ответ, но не форму ответов. Читер со
слитой частью банка решает слитые семейства при любой их трудности, а неслитые — по своему
уровню. Паттерн «решил трудные, не решил лёгкие» плохо объясняется любым одним уровнем, и это
видно по правдоподобию ответов — статистика $l_z$ (Drasgow, Levine, Williams, 1985). При остановке
попытки по её предъявлениям $i$, $p_i = \sigma\big(a_i(\hat\theta_{t(i)} - b_i)\big)$, где
$\hat\theta_t$ — итоговая оценка темы в попытке:

$$l_0 = \sum_i \big[u_i \ln p_i + (1 - u_i)\ln(1 - p_i)\big], \qquad E = \sum_i \big[p_i \ln p_i + (1 - p_i)\ln(1 - p_i)\big]$$

$$V = \sum_i p_i(1 - p_i)\ln^2\frac{p_i}{1 - p_i}, \qquad l_z = \frac{l_0 - E}{\sqrt V}$$

Отрицательный $l_z$ — ответы согласуются с оценкой хуже, чем ожидается от честного кандидата.
Параметры семейств — текущие; скомпрометированные семейства в сумму не входят, их ответы и так
выпали из оценки.

Порог `person_fit_lz` не берётся из стандартного нормального распределения, а подбирается на
настроечном наборе по доле ложных тревог у честных. Адаптивный тест подбирает задания к уровню,
$p_i$ близки к 0,5, и вклад таких заданий в $V$ мал; к тому же $l_z$ считается по оценённому, а не
истинному уровню и смещён (Snijders, 2001). По той же причине чувствительность $l_z$ в адаптивном
тесте заведомо ниже, чем на фиксированном бланке. Сигнал остаётся в правиле подозрительного
результата, только если M22 показывает, что он добавляет пойманных к флагам времени; иначе он
убирается правкой этого раздела.

**События вставки и потери фокуса** пишутся только с согласия кандидата, только как счётчики и
только как сигнал подозрения. Без согласия тест проходится так же.

**Подозрительный результат** — попытка, которая повышает категорию или присваивает её впервые,
плюс хотя бы одно: флагов времени не меньше `rt_flags_for_verification`, событий вставки и
фокуса не меньше `focus_events_for_verification`, $l_z$ попытки не выше −`person_fit_lz`. Попытку, которая категорию не повышает, не
проверяют: защищать нечего. Сигналы считаются по всему определению — дотест каскада продолжает
одно измерение. Согласие на события даётся на попытку; без него счётчики не собираются фронтом и
отбрасываются сервером. Пока результат ждёт блока, попытка на тот же грейд или выше не
начинается, наблюдения определения — вне оценки и профиля, а провалом он не считается: короткий
интервал после провала (§4) он не включает.

**Проверочный блок** — `verification_items` заданий из невиданных кандидатом семейств тех же тем
(если невиданных не хватает, берутся темы попытки, где они есть, затем давно виденные), на время:
`verification_time_limit_minutes` на блок по часам сервера, неотвеченное к сроку считается
неверным. Сложность подобрана так, чтобы при уровне основного теста вероятность верного ответа
была около `verification_target_p`: так блок чувствительнее всего к завышению на грейд. Задания
расходятся по темам: следующее — из темы с невиданными семействами и наименьшим числом заданий
блока, в теме — случайно одно из `exposure_top_k` семейств с P(верно) ближе всего к цели, как
случайный выбор в тесте (§6): порядок заданий блока заранее не известен. Ответы блока — обычные
предъявления: по ним идут калибровка и детектор дрейфа.

Сравнение — проверка согласия. По оценке основного теста ожидаем $E = \sum_i p_i$ верных с
дисперсией $V = \sum_i p_i(1-p_i)$ плюс вклад погрешности основной оценки (дельта-метод);
$z = (X - E)/\sqrt{V}$, где $X$ — число верных. Задание, которое до срока не успели показать,
входит в $E$ с вероятностью `verification_target_p` — блок подбирает сложность под неё — и
засчитывается неверным. Если невиданных и давно виденных семейств не осталось раньше, блок
короче, и сравнение идёт по показанным.

- $z \ge -$`verification_mismatch_z` — **совпал**: категория присваивается по результату попытки,
  наблюдения блока входят в профиль с весом проверочного блока, в профиле пометка «уровень
  подтверждён».
- Иначе — **расхождение**: попытка категорию не повышает, её наблюдения не входят ни в оценку,
  ни в профиль (наблюдения самого блока входят). Кандидат видит причину — «по основному тесту
  ожидалось около 7 верных из 10, получено 2». Категория остаётся прежней, а у кого её не было,
  тот остаётся без категории. Дальше — повторный проверочный блок на тот же грейд через
  `verification_retest_days` или сразу попытка на грейд ниже с чистого листа: её подозрительный
  результат снова проходит через блок.

Сравнение идёт через ожидаемое число верных, а не через две оценки уровня: оценка короткого
блока сильно стянута к априорному и систематически занижала бы сильных честных кандидатов.

**Честно об ограничениях.** По модели десять заданий ловят завышение на два грейда почти всегда,
а на один — примерно в половине случаев; эксперимент это проверит. Против утечки блок силён:
невиданные семейства обнуляют выгоду от слитого банка. Против LLM-помощника слаб: модель решает
и невиданные задания, а время помогает, только если помощь медленная. Блок — облегчённая замена
прокторинга: он поднимает цену обмана, но не исключает его. Высший уровень доверия — ФСП.

Кандидат может пройти проверочный блок и добровольно, чтобы подтвердить уровень, — например, по
рекомендации при расхождении с ФСП (§11). Тогда блок сравнивается с оценкой попытки, по которой
присвоена категория; совпал — пометка «уровень подтверждён», расхождение категорию не меняет.
Повтор после расхождения и добровольный блок — не раньше `verification_retest_days` от старта
прошлого блока; первый блок по отложенному результату — сразу. Пометку снимает смена грейда вверх
без блока: за категорией тогда новая, непроверенная оценка; переход вниз её сохраняет.

**Флаг сам по себе категорию не понижает** и работодателю не показывается — ни флаги времени, ни
события, ни $l_z$. Ложная тревога стоит честному кандидату проверочного блока, а не метки, которую
он не видит и не может оспорить. Работодатель видит только итог проверки — положительную пометку
«подтверждено проверочным блоком»: непроверенный подозрительный результат категорию не повышает и
в выдачу не попадает. В карточке — у категории, в объяснении подборки — у тем, по которым были
задания блока.

## 9. Почему тест устойчив к распространению заданий

ТЗ отвергает два подхода: единый набор заданий разойдётся, а генерация уникальных заданий
нейросетью не гарантирует сопоставимой сложности. Мы генерируем экземпляры из шаблонов с
откалиброванными параметрами семейства, и защита многослойная:

1. **Утёкший экземпляр бесполезен.** Параметры у каждого свои, ответ вычисляется, совпадение
   верных ответов двух экземпляров ограничено `family_answer_collision_max`.
2. **Утёкшее семейство помогает частично и недолго.** Знать тип задания — не то же, что знать
   ответ. Адаптивный выбор, случайность среди топ-k и потолок показов дают каждому малую долю
   банка. Детектор дрейфа замечает семейство, которое решают чаще ожидаемого по уровню
   отвечавших, и выводит его.
3. **Слить весь банк дорого.** Попытки ограничены интервалами смены грейда и повтора после
   провала, шаблоны и генераторы живут только на бэкенде, банк растёт.
4. **Обман неподнадзорного теста упирается в уровни доверия.** Подозрительное повышение категории
   проходит через проверочный блок, а в ранжировании выше стоит ФСП, который не сгенерируешь.
5. **Это измеряется:** кривая атаки утечкой 10 / 30 / 50 % банка для трёх схем теста и точность
   детектора — метрики M14 и M15 [плана валидации](validation-plan.md).

## 10. Почему результаты сопоставимы

1. **IRT учитывает сложность доставшихся заданий:** уровни двух кандидатов, решавших разные
   задания, лежат на одной шкале.
2. **Параметры принадлежат семейству** и оценены на всех его экземплярах; однородность
   экземпляров проверяется (§5).
3. **Якорные семейства** держат шкалу во времени — пороги грейдов не плывут.
4. **Остановка по точности и одно правило уверенности** — у всех одинаковая погрешность на
   финише и одинаковый критерий присвоения.
5. **Это измеряется:** стабильность грейда при повторном прохождении, сходимость калибровки,
   совпадение с истиной — метрики M9, M12, M10.

## 11. Профиль навыков и уровни доверия

**Две оценки на одной модели.** Оценка теста решает категорию (§4). Профиль навыков питает
подбор, карточку и обратную связь: те же $\theta_t$ на той же шкале, но в него входят наблюдения
всех уровней доверия.

**Вес уровня доверия — степень правдоподобия.** Наблюдение с весом $w$ даёт $w \cdot I$
информации; это единый механизм для разнородных сигналов. Вес читается как «сколько стоит одно
наблюдение этого уровня в наблюдениях полного доверия»: чем легче подделать сигнал, тем меньше он
сужает погрешность.

| Уровень | Как становится наблюдением | Вес |
|---|---|---|
| ФСП | Достижение — «решённое задание» сложности $b$ по типу результата — победитель, призёр, финалист (`fsp_result_difficulty`) — и разделяющей силы `fsp_result_discrimination` по темам дисциплины, а в командном зачёте — по темам роли в команде | `trust_weight_fsp` |
| Проверочный блок | IRT-наблюдения, как в тесте | `trust_weight_verification` |
| Адаптивный тест, блок по теме | IRT-наблюдения | `trust_weight_test` |
| Регулярное задание | С эталоном — одна бинарная ступень «верно»; открытое — оценка автора по рубрике 0–3, три ступени: $r \ge 1$, $r \ge 2$, $r = 3$. Каждая ступень — наблюдение по каждой теме задания со сложностью $c_g$ грейда **задания**, у открытого плюс смещение `regular_task_rubric_offsets`, и разделяющей силой `regular_task_discrimination` | `trust_weight_regular_task` |
| Самоописание | В θ не входит; только стек, отдельное слагаемое скора не больше `self_reported_stack_cap` (§12); на категорию не влияет | — |
| Карточка опыта | Показ без веса: ни в одну модель не входит | — |

**Карточка опыта — показ без веса.** Записи опыта — место, роль, период, технологии, что делал —
и годы по технологиям из них работодатель видит рядом с подтверждённым, с пометкой «со слов
кандидата». На оценку уровня, категорию, скор, место в выдаче, модель принятия, обратную связь
кандидату и стенд валидации карточка не влияет, подсказку грейда (§16) не меняет: ранжировать по
опыту из резюме — ровно то, чем накручивают подбор. Записи — раскрываемая часть профиля (§14): в
месте, роли и «что делал» бывают имена, компании и контакты, поэтому до раскрытия их нет ни в
карточке, ни в подборке, ни в поиске. Годы по технологии не вводятся и не хранятся: это длина
объединения периодов записей с технологией на сегодня — пересечения не считаются дважды,
перерывы не считаются, оба месяца периода входят в него, открытый период идёт по текущий месяц.
Месяцы округляются вниз до полугода: семнадцать месяцев — «1 год», а не «почти полтора». Лимиты
формы — `experience_*`.

**ФСП — одностороннее свидетельство.**
$P(\mathrm{result} \mid \theta) = \sigma\big(a(\theta - b)\big)$: сильный результат поднимает
оценку, если она ниже, и почти не влияет, если оценка уже выше. Участие в отборе без выхода в
финал — факт в профиле, а не наблюдение: плохой день на соревновании говорит о навыке меньше, чем
хороший, а онлайн-явками профиль не набить.

**Тип результата, а не уровень мероприятия.** Сложность достижения зависит только от результата:
победитель, призёр, финалист. Мероприятия и дисциплины не ранжируются: организаторы считают все
соревнования ФСП равно важными и не советуют ставить «чемпионат России выше хакатона». Число
соревнований входит само: каждый результат — отдельное наблюдение, и несколько результатов сужают
погрешность сильнее одного. Но свидетельства одного типа упираются в его сложность: десять финалов
говорят «стабильно уровень финалиста», а не «senior». Сложности — стартовые экспертные: победитель —
середина полосы middle, призёр — её порог, финалист — середина junior. Они уточняются, когда у
кандидатов накопятся и ФСП, и тест.

ФСП не меняет ни грейд, ни категорию — только профиль навыков и порядок внутри категории.

**Темы достижения.** Справочник дисциплин (`fsp_disciplines` в `config/catalog.yaml`) сопоставляет
каждой дисциплине темы, о которых говорит результат в ней, — темы любых специализаций; в профиль
идут темы его специализации. Личный зачёт или роль не указана — темы дисциплины. Командный зачёт с
ролью — темы специализации-роли внутри тем дисциплины: фронтендер команды-победителя хакатона
подтверждает вёрстку и фреймворки, а не базы данных; при пустом пересечении — темы роли.
Дисциплина без тем — результат в ней только факт в профиле. Каждый результат с выходом в финал —
наблюдение «решено» по каждой своей теме.

**Порядок и мода.** Наблюдения всех уровней идут в модель по времени сигнала: ответ теста — по
моменту ответа, достижение — по дате мероприятия. У достижения разделяющая сила больше, чем у
задания теста, и один шаг Ньютона от оценки до наблюдения недолетает до моды, поэтому в профиле
каждое наблюдение — до сходимости моды (§3). Оценку теста это не трогает: она считается как
раньше, шагом на наблюдение.

**ФСП ID и реестр.** Вход через ФСП ID — OIDC (authorization code + PKCE) в локальный Keycloak,
который изображает ФСП ID; достижения — из файла-заглушки реестра на синтетике. Настоящий ФСП ID —
смена адреса и ключей в настройках (`FSP_ID_ISSUER`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET`);
реестр — новый адаптер за портом `FspRegistry`, без правки сценариев. Достижения хранятся снимком
с датой получения: снимок обновляют привязка, каждый вход через ФСП ID и «Обновить достижения».
Профиль и подборка читают только снимок — недоступный реестр их не ломает, кандидат видит дату
снимка. Отвязка убирает снимок и наблюдения ФСП из профиля.

**Регулярное задание** работодатель с профилем компании создаёт для любой категории —
специализация × грейд — и отмечает 1–3 темы специализации из справочника. Кандидат с категорией
по тесту берёт задания сам из **каталога**: активные задания своей специализации всех грейдов,
сначала с меньшим числом ответов, при равенстве — новые; фильтры по грейду и теме. Заданий и
ответов сколько угодно, на одно задание — один ответ. Система ничего не предлагает и не
дозирует: кандидат, которому выгодно поднять профиль, и так придёт, а интервал только задержал бы
сигнал.

Задание двух видов. **С эталоном** — короткий ответ строкой или числом — проверяет система, как
семейства банка: сравнение с эталоном после нормализации. Кандидат видит только «ответ принят»,
вердикт уходит в профиль. **Открытое** — скрипт, бизнес-решение — оценивает автор задания по
рубрике: 0 — не решено или не по делу; 1 — частично, подход с ошибками; 2 — верно в целом; 3 —
верно и хорошо: оптимально, с разбором краёв. До оценки ответ на профиль не влияет. Автор видит
ответы обезличенно — под псевдонимом, своим в каждом задании; остальные работодатели — только
влияние на профиль: источник уверенности «подтверждено регулярным заданием» в объяснении
подборки. После первого ответа задание не меняется — ответы оцениваются по его условию; снять
его из каталога можно, наблюдения по нему остаются в профилях.

**Сложность — от грейда задания, а не кандидата.** Верный ответ на middle-задание говорит об
уровне больше, чем на junior: порог $c_g$ — свойство задачи. Сложность кандидата сделала бы одно
и то же решение дешевле для junior и дороже для senior. Задания не меняют ни категорию, ни грейд.

**Свежесть.** Наблюдение профиля несёт момент. Между последовательными наблюдениями к $\Sigma$
добавляется шум $Q\,\Delta t$ по общей части уровня $\theta_s$: дисперсия сообщаемого уровня
каждой темы и общего уровня прибавляет одно и то же $q = $ `profile_decay_sd_per_year`² за год —
$h^\top Q h = g^\top Q g = Q_{ss}$. Ни одна из них не становится выше априорной: $q$ не больше
наименьшего зазора до априорной по темам и общему уровню.

Профиль хранится на момент последнего сигнала. Подборка, карточка, профиль кандидата и PDF
доводят его до «сейчас» тем же шумом — чистой функцией от сохранённых уровней и момента запроса.
Довод по сохранённым уровням совпадает с оценкой, продлённой до «сейчас»: шум прибавляет ко всем
сообщаемым дисперсиям одно и то же, и зазоры до априорной видны по ним. Без новых сигналов
уверенность в выдаче падает сама; если последний сигнал старше `profile_stale_days`, в
объяснении — «давно не подтверждал уровень». Ответ на регулярное задание — сигнал: он снимает
пометку и сужает погрешность. Оценка теста и категория не устаревают и меняются только
попыткой смены грейда.

**Кандидат без ФСП** — полноценный кандидат: в профиле нейтральная пометка «нет истории ФСП»,
профиль — ровно то, что дают его собственные сигналы, как при выключенном модуле ФСП. ФСП не
сдвигает чужие скоры. Меняется только относительный порядок: кандидат с подтверждённым
результатом поднимается выше, как и требует ТЗ.

**Расхождение ФСП и теста.** Если по теме, сопоставленной дисциплине, оценка теста ниже сложности
результата ФСП больше чем на `fsp_divergence_theta`, — пометка и рекомендация проверочного блока.
Профиль считается как обычно, штрафа нет. Тест выше результата ФСП расхождением не считается:
результат ФСП — нижняя граница.

**Кандидат видит свой профиль:** уровень по темам словами, погрешность, из каких сигналов он
сложился и что из этого видит работодатель.

## 12. Подбор

**Категория отсекает.** Скор считается только кандидатам с категорией, присвоенной тестом:
точные — специализация и грейд потребности; «близкие» — та же специализация и грейд на
`nearby_grade_distance` от грейда потребности, отдельным блоком. Кандидат без согласия на
публикацию в выдачу не попадает.

**Нижний блок «Грейд не подтверждён».** Кандидат без категории, заявивший ровно грейд потребности
в её специализации, виден последним блоком выдачи со статусом. Спрятать его — выбросить из
оборота того, кто ещё не прошёл тест или застрял на дотесте; поставить рядом с подтверждёнными —
отдать место заявке, которую тест не подтвердил. Поэтому блок — витрина, а не ранжирование
навыка:

- категория по-прежнему только из теста, нижний блок её не даёт и грейд не меняет;
- скора по темам и P(принятия) у кандидатов блока нет: профиля навыков без категории нет (§11), а
  оценки незаконченной или неудачной попытки он не подтверждает;
- порядок внутри блока — только по доле $o$ технологий потребности в самоописанном стеке, с
  пометкой «по словам кандидата, тестом не подтверждено»; ничьи — тем же хэшем пары
  «подборка — кандидат»;
- блок всегда ниже всех подтверждённых — в сохранённой выдаче, после фильтров и при пагинации:
  самоописание — нижний уровень доверия, и никакое $o$ не перевешивает категорию по тесту;
- соседние грейды в блок не входят: заявка не измерена, «близость» к ней ничего не значит.

Заявленный грейд — грейд первой попытки цепочки определения категории: дотест каскада его не
меняет. Без опроса или без выбранного грейда кандидата в выдаче нет. Кандидат с категорией ниже
заявленной стоит в основных блоках по своей категории — для потребности middle «заявлен middle —
подтверждён junior» попадает в «близкие».

**Статус грейда** виден в карточке и в каждой записи выдачи: «подтверждён тестом» — категория
заявленного грейда; «заявлен X — подтверждён Y» — каскад дал категорию ниже; «заявлен, тест не
пройден» — категории нет: попытка не закончена, предложен дотест или не хватило и для стажёра.

**Требования.** Потребность → темы специализации с важностью: ключевая, важная, желательная. По
умолчанию важность выводится из стека: тема, с которой связано не меньше
`need_key_topic_min_technologies` технологий потребности, — ключевая; одна технология — важная;
ни одной — желательная. Работодатель правит важность чипсами; хранятся только его правки, а
важность остальных тем выводится из стека заново, поэтому смена стека не оставляет устаревших
значений. В стеке — любые технологии справочника: не связанные с темами специализации (Docker у
бэкенда) на важность не влияют, но входят в долю $o$. Вес темы $v_t$ — вес её важности
(`need_importance_weights`), нормированный на сумму. Требуемый уровень по каждой теме — порог
грейда потребности: $\mathrm{req}_t = c_g$. Одно требование на грейд легко объяснить
работодателю и не плодит произвольных надбавок; важность выражается весом.

**Скор соответствия:**

$$S = (1 - \lambda)\sum_t v_t\,P(\theta_t \ge \mathrm{req}_t) + \lambda\,o, \qquad P(\theta_t \ge \mathrm{req}_t) = \Phi\!\left(\frac{\mu_t - \mathrm{req}_t}{\sigma_t}\right)$$

$\mu_t, \sigma_t$ — из профиля навыков; $\lambda$ — `self_reported_stack_cap`; $o$ — доля
технологий потребности в самоописанном стеке кандидата; у потребности без стека $o = 0$ — формула
одна для всех потребностей, а порядок внутри подборки от этого не меняется. По линейности
ожидания первое слагаемое — ожидаемая взвешенная доля выполненных требований. В интерфейсе это
«соответствие N %»; вероятности по темам откалиброваны и проверяются как вероятности (M4).
Самоописание поднимает скор не больше чем на $\lambda$, как бы кандидат ни переписал резюме.

**Объяснение — это и есть скор.** Вклад темы — $(1-\lambda)\,v_t\,P(\theta_t \ge \mathrm{req}_t)$,
вклад стека — $\lambda o$. Сумма вкладов равна скору, обнуление фактора уменьшает скор ровно на его
вклад: объяснение не пишется задним числом.

Формулировки — язык уверенности (`confidence_language_bands`):

- $P \ge 0{,}8$ — «уверенно выше требования»;
- $0{,}5$–$0{,}8$ — «скорее выше»;
- $0{,}2$–$0{,}5$ — «скорее ниже»;
- ниже $0{,}2$ — «ниже требования»;
- $\sigma_t >$ `topic_low_data_sd` — «данных мало».

Рядом — источник уверенности: «подтверждено ФСП», «подтверждено проверочным блоком», «давно не
подтверждал уровень».

**Монотонность:** $\partial S/\partial\mu_t \ge 0$ — рост уровня по нужной теме не опускает
кандидата. Сужение погрешности поднимает того, кто выше требования, и опускает того, кто ниже:
уверенность, что требование не выполнено, — тоже уверенность.

**Порядок** — по взаимному скору (§13), с переключателем «только соответствие». Ничьи
разрешаются детерминированно по хэшу пары «подборка — кандидат», а не по защищённым признакам и
не по дате регистрации.

**Подборка — объект:** снимок потребности, выдача на момент построения со скорами и вкладами,
шортлист. Позже она открывается с той же выдачей. Фильтры применяются поверх и её не
перезаписывают, сброс возвращает исходный порядок; перестроение создаёт новую подборку.
Удаление потребности подборку не уносит: она открывается по снимку, а места кандидатов в
подборках остаются историей для обратной связи (§15). Пока модели принятия нет, P(принятия) в
выдаче не показывается, а не выдаётся за 100 %.

**Поиск по банку** — те же обезличенные карточки и фильтры: специализация, грейд, категория, стек,
подтверждённые достижения ФСП, уверенность в уровне (погрешность общего уровня по профилю не выше
`search_confident_sd`). Без потребности внутри категории порядок — по $P(\bar\theta \ge c_g)$ по
профилю: выше те, в чьём уровне система увереннее. Это и есть «сила подтверждённого профиля» из ТЗ.

**Разбор потребности из текста** — локально, за портом `TextUnderstanding`
([adr/0002](adr/0002-text-understanding-port.md)): правила и словарь синонимов или локальная
LLM через llama.cpp. Текст во внешние API не уходит. Выход — черновик: специализация, грейд,
стек, формат, город и вилка, у поля — уверенность. Модель отдаёт только значения справочника,
сценарий проверяет их сам и отбрасывает остальное. Важность тем черновик не несёт — её выводит
стек, как у формы. Вилку разбор берёт как написана: «на руки» не пересчитывается, поле
подсвечивается.

Экран «система поняла так» показывает черновик полями формы: неуверенные — уверенность ниже
`need_draft_confident` — и не найденные в тексте выделены. После правки — «Сформировать
подборку» без сохранения потребности: та же подборка, что по сохранённой, со снимком черновика.
Правка и новый вызов — новая подборка, прежняя открывается с той же выдачей. Черновик
сохраняется обычной потребностью только по решению работодателя.

Вне справочника (1С, геймдев и т. п.) — честный ответ «такой специализации нет» и ближайшие
специализации кнопками: выбор открывает черновик с ней, пустой выдачи нет. Решает перевес
упоминаний: упоминание 1С в тексте про бэкенд не делает его текстом про 1С.

## 13. Взаимный скор и модель принятия

**Порядок подборки** — $S \times P_{\mathrm{accept}}$. Работодателю мало подходящего кандидата,
нужен тот, кто скажет «да», а лучшим кандидатам не нужны полсотни приглашений, которые они не
примут.

**P(принятия)** — классификатор CatBoost. Признаки — пара «потребность — кандидат» числами
(`app/domain/acceptance.py`), одни и те же при обучении и в проде:

- вилка относительно ожиданий кандидата — $\ln(\text{середина вилки} / \text{ожидание})$;
- вилка относительно рынка — $\ln(\text{середина вилки} / \text{медиана})$, медиана —
  `market_salary_median` грейда категории кандидата: что кандидат получил бы на рынке;
- грейд категории;
- совпадение формата работы; совпадение города с учётом готовности к переезду — у удалённой
  потребности город не важен;
- загрузка кандидата открытыми приглашениями — отправленные и просмотренные, не истёкшие;
- соответствие $S$;
- сфера бизнеса компании среди интересных кандидату сфер; не отметил — не совпала.

Нет ожиданий кандидата — пропуск, модель решает сама, куда он идёт. **Потребность без вилки** —
P не считается: множитель 1, в выдаче `null`, рыночная медиана вместо вилки не подставляется.

**Рыночная вилка** — таблица медиан по грейду в конфиге, а не квантили ожиданий кандидатов
категории: на синтетике квантили замкнуты на ту же таблицу, а в проде данных мало и их можно
накрутить, заявив ожидания. Прод и стенд читают одну таблицу.

**Активности в признаках нет.** Время последнего входа можно было бы хранить, но честного
источника для обучения нет: на синтетике признак был бы выдуман вместе с ответом на него.
Признак вернётся вместе с меткой доверия компании, когда появятся реальные отклики.

Защищённых признаков нет (§17). **Монотонные ограничения:** выше вилка — оба вилочных признака —
вероятность не ниже; больше открытых приглашений — не выше. **Объяснение** — SHAP, точно
аддитивный в логит-пространстве модели.

**Обучение** — на поведении синтетических кандидатов, одной командой стенда
`uv run python -m validation acceptance`, на своём сиде, отдельном от D1 и D2. Пары — подборки
по потребностям, построенные теми же сценариями, что HTTP: top-`acceptance_train_top_k` по $S$ на
потребность и `acceptance_random_share` от K случайных кандидатов той же подборки сверх них;
20 000 пар. Загрузка кандидата пары — Пуассон со средним
`acceptance_load_mean` · (0,5 + перцентиль $S$ в подборке): сильных зовут чаще.

**Решение синтетического кандидата** — скрытая истина стенда:

$$\operatorname{logit} P = \operatorname{logit}(a) + c_0 + w_s(x)\,x + w_f + w_c + w_i + w_l\,n,$$

где $a$ — склонность кандидата принимать приглашения из истины, $x$ — логарифм вилки к
ожиданию, $w_s$ — `acceptance_w_salary_below` при $x < 0$ и `acceptance_w_salary_above` при
$x \ge 0$, $w_f$ — штраф за несовпадение формата, $w_c$ — за город (готовому к переезду —
меньший), $w_i$ — прибавка за совпадение сферы, $n$ — открытые приглашения. Рыночная медиана в
правило не входит — только в признаки модели. Решение — Бернулли. Модель учится на решениях и
склонности $a$ не видит; веса зафиксированы до первого обучения, M7 идёт в отчёт как получилась.

Обучение — только CPU: монотонные ограничения CatBoost есть только там. Сид и число потоков
фиксированы в конфиге — повторный запуск даёт ту же модель и те же метрики. Файл модели
`backend/app/adapter/acceptance_model.cbm` версионируется в репо, прод его загружает; файла нет —
множитель 1, и подборка работает по одному соответствию. Метки для дообучения на реальных данных —
статусы приглашений и откликов: принято — 1, отклонено и истекло — 0.

**Подсказка по вилке** — в форме приглашения, для кандидата из выдачи подборки. Работодатель
видит P(принятия) при своей вилке и самую низкую вилку, при которой P достигает
`acceptance_target_probability`. Считается по признакам строки на момент построения подборки
(они лежат в строке выдачи и наружу не отдаются), только вилка подставляется своя.

- **Сетка.** Вилки той же ширины, что у введённой (до `salary_hint_rounding_rub`), с «от» кратным
  шагу: от шага до `salary_hint_market_ratio` рыночных медиан грейда кандидата. P не убывает по
  вилке (монотонные ограничения), поэтому порог один — берётся первая вилка сетки с P не ниже
  цели. P считается по самой вилке подсказки, уже округлённой, так что округление не уводит её
  ниже цели.
- **Недостижимая цель.** Ни одна вилка сетки не даёт P ≥ цели — подсказки нет, интерфейс так и
  говорит; вилка не выдумывается.
- **Ожидание не раскрывается.** Границы подсказки кратны шагу, а P при вилке работодателя
  считается по вилке, округлённой до того же шага (ответ называет, по какой): точная P при
  произвольной вилке позволила бы перебором найти ожидание кандидата точнее шага.
- **Без файла модели** P нет, подсказки нет, ответ `available: false` без ошибки; форма и
  подборка работают, множитель 1. То же — у потребности без вилки и у кандидатов нижнего блока.

**SHAP-объяснение P** — в строке подборки: вклады факторов в логит модели, точно аддитивные:
база плюс сумма вкладов равна логиту P (проверка M8 плана валидации, допуск $10^{-6}$). Факторы —
вилка (оба вилочных столбца сложены: делить вклад между ними нечем), грейд, формат, город,
загрузка, соответствие, сфера. Вклад вилки показывает, повышает ли вилка P или снижает, ожидание в
рублях не отдаётся.

**Переключатель «только соответствие»** — вид подборки: внутри блока порядок по $S$, а не по
$S \times P$; блоки не смешиваются, ничьи остаются в сохранённом порядке, места пересчитываются.
Сохранённая выдача от переключателя не меняется.

## 14. Рынок

- **Все суммы — рубли в месяц до вычета НДФЛ (гросс).** Ожидания кандидата, вилки потребности,
  приглашения и вакансии — в одной единице, и модель принятия сравнивает их напрямую, без
  пересчёта налога. Каждая сумма подписана: в формах — «до вычета НДФЛ», в ответах API — поле
  `salary_basis`. Организаторам всё равно, гросс или нетто, лишь бы было подписано; гросс — потому
  что так работодатель планирует бюджет.
- **Вилка «от–до» в рублях** обязательна в приглашении и вакансии: обе границы больше нуля,
  «от» не больше «до». В потребности вилка необязательна — работодатель может ещё не знать её,
  для этого и подсказка по вилке (§13); указанная проверяется по тем же правилам.
- **Бюджет приглашений** — `invitation_weekly_budget` на компанию за календарную неделю, с
  понедельника 00:00 по Москве. Отклонённые и истёкшие приглашения в бюджет не возвращаются:
  иначе каждый отказ освобождал бы место для следующего приглашения, и бюджет перестал бы
  ограничивать рассылку. Отклики на бюджет не влияют.
- **Одно открытое приглашение** компании кандидату: следующее — после закрытия прошлого.
- **Срок ответа** — `invitation_ttl_days`, потом «истекло».
- **Статусы:** отправлено → просмотрено → принято, отклонено или истекло. Переходы проверяет
  бэкенд.
- **Вакансия** — публичная витрина работодателя, с потребностью не связана: название,
  описание, специализация, грейд, форматы работы, вилка. Снятая с публикации уходит из общего
  списка, откликнуться на неё нельзя, поданные отклики остаются; править её нельзя.
- **Отклик** — инициатива кандидата: на вакансию — один раз, и без категории. Статусы и срок
  ответа — те же, что у приглашения, ход у работодателя: открыл отклик — «просмотрено», дальше
  принял или отклонил. Бюджет приглашений и правило одного открытого приглашения откликов не
  касаются: отклик — решение кандидата, рассылкой он быть не может.
- **Обезличенная карточка** — до принятия приглашения или собственного отклика: без ФИО, фото,
  возраста, вуза и контактов. Свободный текст — «о себе», роли, софт-скиллы, карточка опыта
  (§11) — до раскрытия не показывается: в нём бывают имя и контакты. Достижения ФСП везде показываются как
  подтверждённые, отдельно от самоописания; в карточке они обобщены: тип результата,
  дисциплина, год — без названия мероприятия и места, потому что таблицы результатов публичны,
  и по точному мероприятию с местом человека находят по фамилии.
- **Видимость самоописания** — кандидат переключателями в анкете скрывает из обезличенной
  карточки любое из пяти полей: стек, стаж, город, готовность к переезду, интересные сферы. По
  умолчанию видно всё — и у новой анкеты, и у профилей, заполненных до появления настройки.
  Форматы работы, категория, профиль навыков и достижения ФСП видны всегда: без них карточка не
  отвечает на вопрос, подходит ли кандидат. Скрытое поле в карточке пусто и названо в списке
  скрытых — «скрыто кандидатом» не путается с «не заполнено». Настройка действует только до
  раскрытия: после принятого приглашения или отклика компания видит анкету целиком. Подбор и скор
  читают скрытые поля как раньше — настройка меняет проекцию, а не отбор, и объяснение подборки
  (совпавшие технологии) она не трогает. PDF-профиль всегда полный: его кандидат отправляет сам.
- **Раскрытие** контактов и полного профиля — только компании, чьё приглашение принято или на
  чью вакансию кандидат откликнулся, пока кандидат не отозвал доступ. Отклик раскрывает сразу и
  в любом статусе: кандидат сам решил показаться, — и открывает компании его карточку, даже если
  категории и заявленного грейда нет. Проверяется на бэкенде на каждом эндпоинте, отдающем
  данные кандидата.
- **Переписка** — внутри принятого приглашения, только текст: списаться на платформе удобнее,
  чем обменяться контактами. Пишут и читают две стороны — кандидат-адресат и компания-отправитель;
  остальным переписка не существует, как чужое приглашение. В отправленное, просмотренное,
  отклонённое или истёкшее приглашение не пишут. Текст не фильтруется — кандидат сам решает, что
  писать; предел длины — `message_max_length`. Непрочитанное — сообщения другой стороны, которые
  эта сторона ещё не открывала: счётчик в кабинете и у каждого приглашения, без почты.
- **Отзыв доступа** — кандидат отзывает доступ по своему принятому приглашению или отклику, и
  компания снова видит обезличенную карточку во всех ответах с данными кандидата. Отзыв
  закрывает все принятые приглашения этой компании кандидату и все его отклики на её вакансии,
  другие компании доступ сохраняют; повторный отзыв ничего не меняет. Вернуть доступ нельзя:
  данные снова раскрывает только новое приглашение той же компании, принятое кандидатом, или
  отклик на другую её вакансию — на ту же откликаются один раз; отозванное приглашение уже
  закрыто, новое отправить можно. Переписка после отзыва продолжается: отзыв
  скрывает карточку, а не разговор, и обе стороны пишут дальше.
- **Ожидаемая зарплата** кандидата работодателю не показывается и после раскрытия: она — признак
  P(принятия), а не условие торга. Поэтому её нет ни в карточке, ни в PDF-профиле — PDF кандидат
  может отправить работодателю сам.

## 15. Обратная связь кандидату

Считается по подборкам за `feedback_period_days`, в которые попал кандидат. Работодатели, их
потребности и чужие профили кандидату не показываются.

- **Порог k — по компаниям.** Агрегаты и подсказки показываются, только если кандидата включили
  подборки не меньше `feedback_min_companies` разных компаний. Порог по числу подборок не
  защищает: пять подборок одной компании по одной потребности раскрывают её. Ниже порога —
  нейтральное «пока мало подборок» и общая подсказка: блок по теме категории с наибольшей
  погрешностью.
- **Агрегаты:** число подборок, медианное место в общей выдаче (сначала точные, затем «близкие» —
  то место, что видел работодатель) и доля подборок, где кандидат стоял в точном блоке.
- **Что поднимет выше** — контрфактически той же функцией скора, что и подборка (§12). Каждая
  встреченная потребность берётся один раз, по снимку из последней подборки; профиль —
  текущий. По каждой теме потребности два сценария:
  - *сужение погрешности* — прогноз ковариации после блока по теме по формуле обновления §3:
    `topic_block_items` наблюдений по теме с $b = \mu_t$ (адаптивный выбор берёт задания около
    уровня), $a$ — среднее по семействам темы, $w$ = `trust_weight_test`. Обновление $\Sigma$
    от исхода ответа не зависит, $\mu$ не меняется;
  - *рост уровня на полосу* — $\mu_t + 1$ при той же погрешности (полоса грейда шириной 1).

  Прирост темы — лучший из двух сценариев, усреднённый по потребностям; отрицательный
  отбрасывается. Сужение опускает скор там, где уровень ниже требования, — тогда подсказка
  говорит о росте уровня, а не обещает его за одно прохождение блока. Подписью — средний выигрыш
  мест против сохранённых в подборке скоров соседей, без их текущих профилей. Показываются до
  `feedback_hints_max` тем с приростом не меньше `feedback_min_gain`.
- **Действие** у подсказки по теме — ответить на регулярное задание, если оно есть по теме, иначе
  пройти блок по теме (§6); до конца интервала блока по теме действие недоступно и несёт дату,
  когда можно. Привязка ФСП ID — отдельная подсказка без числа прироста, если ФСП не
  привязан: у достижений до привязки нет уровня, и отсутствие ФСП не штрафуется (§11).

## 16. LLM и персональные данные

- **LLM не ставит оценок и не ранжирует.** В продукте — локальная модель через llama.cpp:
  разбор текста за портом `TextUnderstanding` (только значения справочника, подтверждение
  человеком, запасной путь на правилах — [adr/0002](adr/0002-text-understanding-port.md)),
  пересказ посчитанных цифр (числа и темы сверяет код, при расхождении — данные без текста) и
  чат-поиск поверх тех же сценариев подбора (порядок — только из функции скора, сужение —
  видимыми фильтрами). Без модели работают правила и форма.
- **Вне продукта** — офлайн-черновики шаблонов заданий с ревью человеком и стенд валидации:
  атакующий «LLM-помощник» и базовая линия «LLM-ранжировщик», только синтетика и задания банка;
  какие модели и как запускались — в отчёте стенда. Ответы кэшируются в репо, отчёт
  пересобирается без сети.
- **Персональные данные во внешние API не уходят:** резюме и потребности разбираются локально.
- **Текст из PDF очищается** от скрытого текста (белого, нулевого размера, за полями страницы) и
  инструкций. Распознанное попадает только в самоописание — низший уровень доверия.

**Резюме из PDF.** Порт `ResumeText` отдаёт только видимый текст: обход потока содержимого
страницы повторяет состояние графики и выбрасывает показ текста светлее `resume_max_lightness`
на белом с учётом прозрачности и цветового пространства, в невидимом режиме отрисовки, с кеглем
на странице меньше `resume_min_font_pt`, с началом за краем страницы — и после сдвига кернингом
или подъёмом — и с интервалами, которыми буквы разносят за край. Распакованное содержимое — не
больше `resume_max_content_bytes`. Затем `cleaned` убирает невидимые знаки, и правила собирают черновик
анкеты: ФИО и контакты — по виду, стек — по справочнику, роли и софт-скиллы — названиями записей
словаря, а не фразами текста; так инструкция из резюме не протечёт ни в одно поле. Стаж — прямое
«опыт N лет», иначе объединение периодов работы в разделе опыта, неуверенно. Черновые записи
опыта (§11) — по периодам раздела опыта: текст записи — от её периода до следующего, место — первая
строка записи без частей, которые называют роль, роль — название из словаря ролей в той же
строке, технологии — справочника во всём тексте записи; «что делал» пусто — его пишет кандидат.
Без заголовка раздела опыта записей нет: годы учёбы — не опыт. Записи всегда подсвечены как
неуверенные, а запись, которую форма не примет, — без места, с периодом в будущем или концом
раньше начала — отбрасывается. Файл больше
`resume_max_bytes` или длиннее `resume_max_pages`, битый и без текстового слоя — понятная ошибка.
Ни файл, ни черновик не сохраняются: профиль меняет только форма, которую кандидат подтвердил.

**Подсказка грейда** — по стажу и ролям сохранённого профиля: грейд по стажу — на порогах
`experience_years` словаря синонимов, тех же, что у разбора потребности; грейд по ролям — по словам
грейдов в ролях. Подсказка — младший из двух: роль «тимлид» при двух годах стажа не тянет её
вверх. Видна на шаге выбора грейда, грейд не выбирает и на категорию не влияет — его проверяет
тест. Записи опыта в подсказку не входят.

## 17. Защищённые признаки

Пол, возраст и вуз не входят ни в одну модель: ни в оценку уровня, ни в скор соответствия, ни в
P(принятия). У каждой модели рядом с ней в домене объявлен список признаков: у оценки уровня —
`SKILL_MODEL_FEATURES`, поля наблюдения; у скора — `MATCH_FEATURES`, входы `match_score`; у модели
принятия — `ACCEPTANCE_FEATURES`, поля `AcceptanceFeatures`. Тест сверяет каждый список с тем, что
модель на деле получает, — новый признак без объявления валит его, — и проверяет, что ни один
список не пересекается со стоп-листом защищённых имён: пол, возраст, дата рождения, вуз,
образование. Стоп-лист ловит имена, а не смысл: признак под другим именем ловит ревью
объявленного списка.
В карточке до раскрытия их нет.
Платформа их и не собирает: в профиле кандидата нет фото, даты рождения и вуза — чего нет, то не
утечёт и не попадёт в модель (минимизация данных по 152-ФЗ).
