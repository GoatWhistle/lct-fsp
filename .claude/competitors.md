Файл внутренний: `.claude/` вырезается при сдаче, в репо жюри не попадает.

**Как читать.** Про чужие репозитории — только то, что написано в их README и docs; код не клонировался и
не запускался. Их цифры — самоотчёт на собственной синтетике, с другим генератором и другими порогами, поэтому
напрямую с нашими не сравниваются. Про нас — по `README.md`, `docs/validation-report.md` и коду в `main`.

## 2. fsp-career: что заявлено

- **Стек.** FastAPI, SQLAlchemy, PostgreSQL 16, React 18/TS/Vite/Tailwind, Docker Compose. Модульный монолит `api → services → models`, ядро теста без БД.
- **Банк.** 359 семейств, 27 доменов, 7 специализаций × 4 грейда = 28 категорий.
- **Тест.** IRT 3PL, EAP, выбор по информации Фишера с балансом и контролем показов; полный тест 12–24 задания (в среднем 20,4), экспресс-тест на 8 заданий без категории. Остановка: SE ≤ 0,28 или оба порога решены с уверенностью ≥ 0,92.
- **Категория.** Грейд подтверждён при P(θ ≥ нижняя граница) ≥ 0,6. Неподтверждённые — внизу выдачи.
- **Скор подбора.** `(0,30·навыки + 0,25·сила профиля + 0,20·категория + 0,15·условия + 0,10·текст) × доступность`. Вес ФСП — около 6 % максимума; по их же замеру без ФСП P@10 0,835 → 0,840, то есть в шуме.
- **Защита.** Три детектора («чужой вариант», дрейф решаемости, person-fit), скриншот-прокторинг, песочница без сети, антиплагиат кода.
- **LLM.** Только черновики заданий при подготовке банка; в тесте и подборе не участвует. Локально, Qwen3-14B через Ollama.
- **ФСП ID.** OIDC (code + PKCE), Keycloak-совместимые пути, проверка `id_token` по JWKS; на стенде — мок.
- **Рынок.** Приглашение с вилкой, лимит 60 в сутки на компанию, индекс доверия компании, согласия по 152-ФЗ, выгрузка и удаление данных, аудит доступа к контактам. Вероятность принятия — метка «высокая/средняя/низкая» из логистической формулы, замеров нет.
- **Валидация (самоотчёт).**

| Метрика | Значение | База |
|---|---|---|
| Точное совпадение грейда / ±1 | 64 % / 95 % | резюме 57 % |
| Завышение грейда | 3,1 % | резюме 36 % |
| Повтор: κ / r(θ) | 0,80 / 0,82 | — |
| Атака утечкой, необнаруженное завышение | 13,0 % | честные 12,1 %; фиксированный тест 97 % |
| P@10 / nDCG@10 / MRR | 0,84 / 0,82 / 0,96 | фильтры резюме 0,75; ключевые слова 0,27 |
| Нагрузка | 800 пользователей, ошибок нет, p95 ≤ 1 с | одна машина |

- **Оговорки самих авторов.** Вся валидация на синтетике (1500 кандидатов для теста, 900 и 60 потребностей для подбора, 35 % накрутчиков); план до прогона не заявлен; выборки по коду (19 случаев) и PDF (80) малые; ФСП — мок; LLM-задания требуют ручной проверки и пилота на 40 ответах.
- **Упаковка.** Презентация PDF/PPTX, документация PDF/DOCX, `pitch.md` со сценарием выступления и запасным видео, страница «Проверка подбора» (`/evaluate`) для проверки на своих данных.

Условные обозначения: **Мы+** — у нас сильнее, **Они+** — у них сильнее, **≈** — паритет или не проверить.

### 3.2. Сводка по сильным сторонам

**У нас сильнее (и это не надо терять):**
1. Принцип «утверждение о качестве — только с экспериментом по плану до прогона»; негативные результаты в отчёте открыто. Жюри оценивает «качество процедуры валидации» отдельной строкой ТЗ.
2. Профиль навыков с погрешностью и уровнями доверия; вероятностная семантика скора; калибровка вероятностей (M4 пройдена).
3. Модель принятия с монотонностью по вилке и загрузке, без защищённых признаков по построению.
4. Правила приватности и раскрытия как единое доменное правило; отзыв доступа; переписка внутри приглашения.
5. Строгая архитектура (порты, тесты слоёв) и объём тестов.
6. Политика LLM: не ставит оценок, не ранжирует; одна локальная модель в сдаче.
7. Обратная связь кандидату с порогом k по компаниям.

**У них сильнее (то, на чём нас будут сравнивать):**
1. **Итоговые цифры.** Заявленное завышение 3,1 %, κ 0,80, необнаруженная накрутка при утечке 13 % — против наших M14/M15/M16 «не выполнен» и κ 0,58–0,65. Жюри видит таблицу с цифрами, а не разницу в строгости методики.
2. **Защита от утечки заявлена как работающая.** У нас детектор дрейфа ловит 7–14 % слитых семейств при пороге 80 %.
3. **Адаптивность.** Они заявляют 12–24 заданий, в среднем 20; у нас M13 не пройдена (до 27–32 заданий в части специализаций).
4. **Размах.** 7 специализаций (у нас 5), экспресс-тест без регистрации, песочница для задач с кодом, антиплагиат.
5. **Нагрузка и деплой.** 800 пользователей, публичный стенд.
6. **Упаковка и питч.** Презентация, PDF/DOCX, видео, страница самопроверки подбора для жюри.
7. **Метрика релевантности выше нашей сравнительной.** При их P@10 0,84 против резюме 0,75 они выигрывают у базовой линии; мы у наивного теста — проигрываем.

**Слабые стороны обоих:** вся валидация на синтетике; ФСП ID и реестр — моки; нет живого пилота.

### 3.3. Честные оговорки к сравнению

- Их 64 % точного совпадения против наших 54–59 % **не сравнимы**: разные генераторы, разные доли накрутчиков, разные определения истины и каскада.
- Их заявленная «база» (резюме 57 %, ключевые слова 0,27) слабая; наша база — наивный тест B0, **сильнее**. Они сравнивались с более лёгким противником.
- У нас в M10 завышение мало (0,017), но занижение велико (0,39) — это цена консервативного правила, и мы сами называем её в README. У них занижение не раскрыто.
- Утверждения про их защиту (три детектора, песочница, 13 %) я не проверял кодом.
- Возможно, что у них есть то, чего нет в README; и наоборот.

## 4. Что из этого следует

### Приоритет: закрыть разрыв там, где нас сравнят по цифрам

1. **M13 и размер банка.** В отчёте предел — 2–5 семейств на грейд темы; пока банк тонкий, адаптивность не работает. Банк (402 семейства) уже сопоставим с их 359 — вопрос в распределении по ячейкам «тема × грейд».
2. **M14/M15.** Если за 20 дней нельзя довести детектор дрейфа, честно выносить в питч: «защита — многоуровневая, вот что ловит, вот что нет», плюс сильная сторона — проверочный блок на честных (M17 пройдена: ложных срабатываний почти нет).
3. **M1/M2 сравнительная часть.** Базовые линии B1–B3 (BM25, эмбеддинги, LLM-ранжировщик) ещё не прогнаны; без них «ожидает данных» выглядит как пробел. Это дешёвый способ получить таблицу «мы против рынка», сопоставимую с их «против ключевых слов».
4. **Нагрузка (M23).** Замер подборки на 1000 кандидатах и простой нагрузочный прогон — закрывает их козырь.

### Не делать

- Не копировать веса их скора «руками»: наш подход честнее, и на нём построен главный аргумент.
- Не гнаться за их числами, подгоняя генератор: это нарушает наш же принцип «план до прогона».

### Питч

- Позиционирование: «подбор, который нельзя накрутить» + «мы показываем, где он ломается». Прямо сказать, где нас обходит наивный тест и почему (консервативная категория), и показать цену/выгоду: завышение в 8 раз ниже наивного теста.
- Подготовить слайды, запасное видео и сценарий на 1 и 3 минуты — у соперника это уже есть.
- Ответ на вопрос жюри «чем вы отличаетесь от fsp-career»: вероятностный профиль с погрешностью и уровнями доверия; модель принятия с ограничениями; план валидации до прогона; открытые отрицательные результаты; политика LLM.

### Проверить вручную

- Недоступные страницы `SergeyFilyanov/fsp-talent` и `Zhaba1337228/lct_hackathon_fcp` (возможно, приватные или переименованы).
- Поднять `docker compose up` у fsp-career (порт 8080) и пройти его сквозной сценарий рядом с нашим — это даст сравнение интерфейса и скорости без догадок.
- Сверить его валидацию с кодом: `python -m validation.run_all`.
