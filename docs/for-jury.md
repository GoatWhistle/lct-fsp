# Для жюри

Маршрут по стенду за 15 минут и где в репо ответ на каждый критерий оценки ТЗ. Как поднять
стенд — [запуск](running.md), коротко: `docker compose up --build`, затем
`docker compose exec backend python seed_demo.py`.

Пройти тесты самому без регистрации — режим жюри: `DEMO_MODE=true docker compose up --build`, на
странице входа «Войти как работодатель» и «Новый тестовый кандидат» ([механики, §18](mechanics.md#18-режим-жюри)).
Экспресс-тест — 8 заданий; не хватило уверенности для категории — предложение продолжить полный.

Пароль демо-учёток — `demo-2026`, участников ФСП ID — `fsp-demo-2026`.

## Сквозной сценарий

Шаги повторяют требования ТЗ к демонстрации (§3.3): регистрация соискателя, опрос и тест,
категория, поиск работодателем, выход на контакт, отклик на вакансию. Тот же сценарий
автоматизирован в `frontend/e2e/defense.spec.ts` и проходит на демо-данных.

| # | Что сделать | Что увидеть | Что это доказывает |
|---|---|---|---|
| 1 | http://localhost:3000 → «Регистрация» → «Кандидат» → письмо в http://localhost:8025 → ссылка | вход открыт только после подтверждения адреса | регистрация по email с подтверждением |
| 2 | Опрос: направление → выбор грейда | подсказка грейда по стажу и ролям профиля, выбор — за кандидатом | грейд выбирает кандидат, проверяет тест |
| 3 | Тест: ответить на 5–10 заданий | «задание N, не больше 30», ввод ответа, выбор, перестановка; у другого кандидата — другие задания | у каждого свои экземпляры, эталон вычисляется кодом |
| 4 | Довести тест до конца или войти как `backend-middle@demo.example` | уровень с погрешностью, вероятность каждого грейда, категория, профиль по темам | категорию определяет тест по правилу уверенности |
| 5 | Выйти → «Войти через ФСП ID» → `fsp-winner` | достижения в профиле, темы «подтверждено ФСП» | связь с ФСП ID через OIDC, ФСП — высший уровень доверия |
| 6 | Войти как `backend-junior@demo.example` | профиль с нейтральной пометкой «нет истории ФСП», без штрафа | корректная обработка кандидата без ФСП |
| 7 | Войти как `employer@demo.example` → «Потребности» → «Описать словами» → вставить текст вакансии | «система поняла так»: поля формы, неуверенные выделены | разбор потребности из текста, локально |
| 8 | «Сформировать подборку» | блоки: точный грейд, «близкие», «грейд не подтверждён»; у каждого соответствие и P(принятия) | выдача из категорий теста, порядок по силе подтверждённого профиля |
| 9 | Открыть кандидата → объяснение; «Как считается» | вклад каждой темы и стека, сумма вкладов равна соответствию | объяснимость выдачи из самой формулы |
| 10 | Фильтр по стеку или ФСП → сбросить | выдача сужается и возвращается к исходной | уточнение без потери подборки |
| 11 | «Кандидаты» → поиск по банку: специализация, грейд, ФСП | обезличенные карточки по силе подтверждённого профиля | поиск по всей базе с фильтрами ТЗ |
| 12 | «Пригласить» → описание и вилка «от–до» → отправить | бюджет недели уменьшился, статус «отправлено» | обратная механика: инициатива у работодателя |
| 13 | Войти приглашённым кандидатом → «Приглашения» → открыть | вилка и компания видны до начала общения; статус у работодателя — «просмотрено» | условия до общения, статусы у обеих сторон |
| 14 | «Принять» → написать сообщение | работодатель видит ФИО, контакты и переписку | контакты раскрываются только после принятия |
| 15 | Работодатель: «Вакансии» → опубликовать; кандидат: «Вакансии» → откликнуться | отклик у работодателя сразу с профилем, бюджет не тратится | классический отклик как дополнительный сценарий |
| 16 | Работодатель: «Задания» → новое задание на категорию; кандидат: ответить | ответ под псевдонимом, оценка по рубрике сдвигает профиль | регулярные задания от работодателя |
| 17 | Кандидат: «Скачать PDF», переключить язык | профиль единого вида на русском или английском | стандартизированный PDF-профиль |
| 18 | Сузить окно до 375 px, переключить тему | интерфейс без горизонтальной прокрутки, обе темы | адаптивная версия |

## Где ответ на каждый критерий

### 1. Новая механика подбора — 35 %

| Что оценивается | Где ответ |
|---|---|
| Сценарий выхода на контакт | приглашение с обязательной вилкой, бюджет 20 в неделю, одно открытое приглашение компании кандидату, контакты только после принятия — [механики, §14](mechanics.md#14-рынок) |
| Применимость для обеих сторон | порядок по S × P(принятия): работодателю — тот, кто скажет «да», лучшим кандидатам — не полсотни приглашений; кандидату — обратная связь «что поднимет выше» — [§13](mechanics.md#13-взаимный-скор-и-модель-принятия), [§15](mechanics.md#15-обратная-связь-кандидату) |
| Обоснованность ранжирования | категория отсекает, внутри — вероятность выполнения требований по темам из профиля навыков; самоописание с потолком — [§12](mechanics.md#12-подбор) |
| Объяснимость выдачи | объяснение — слагаемые скора, сумма равна скору — [§12](mechanics.md#12-подбор), шаг 9 маршрута |
| Доля релевантных в топе выдачи | M1 0,890 на D1 и 0,832 на D2 при пороге 0,70; разбор, почему наивный тест выше, — [отчёт, M1](validation-report.md#m1-доля-релевантных-в-топ-10) |
| Реальный сценарий | шаги 7–14 маршрута |

### 2. Механика тестирования, валидация и категоризация — 25 %

| Что оценивается | Где ответ |
|---|---|
| Устойчивость к распространению заданий | семейства с экземплярами из seed, эталон кодом, адаптивный выбор с потолком показов — [§5](mechanics.md#5-семейства-заданий), [§9](mechanics.md#9-почему-тест-устойчив-к-распространению-заданий); что из защиты ещё не подключено — [README, ограничения](../README.md#ограничения) |
| Стабильность грейда при повторе | M9: κ 0,649 и 0,616 против 0,517 у наивного теста — [отчёт](validation-report.md#m9-стабильность-грейда) |
| Дискриминативность заданий | M11: все 340 калибруемых семейств разделяют слабых и сильных; проверка согласия выводит порченые — [отчёт](validation-report.md#m11-дискриминативность-семейств) |
| Соответствие эталонной разметке | M10: завышение 0,017 против 0,137 у наивного теста, матрица «истинный × присвоенный» — [отчёт](validation-report.md#m10-совпадение-грейда-с-истиной) |
| Корректность категоризации | категория — специализация опроса × грейд теста, каскад вниз, правило ожидания — [§4](mechanics.md#4-категория-и-правило-уверенности) |
| Качество процедуры валидации | план до прогона со скрытой истиной, генератор со сдвигом, базовые линии, журнал правок — [план](validation-plan.md); отрицательные результаты — в отчёте как есть |

### 3. Удобство интерфейса — 10 %

Свой интерфейс в цветах брендбука ФСП, RU и EN, светлая и тёмная тема, проверка доступности axe
по WCAG 2.1 AA на 18 экранах в обеих темах (`frontend/e2e/axe.spec.ts`). Путь кандидата
ведёт сам: без категории кабинет открывается на следующем шаге пути.

### 4. Техническая проработка — 7 %

Слои с портами на каждую заменяемую реализацию, проверка направления импортов тестом, строгий
mypy, OpenAPI из кода — [архитектура](architecture.md). Тесты трёх уровней на бэкенде, 29
правил проекта, юнит-тесты и e2e на фронте — [запуск и проверки](running.md#тесты). Бэкенд без
состояния в памяти: попытка восстанавливается пересчётом, экземпляров можно поднять несколько.
