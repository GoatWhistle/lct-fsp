# Схема сбора результатов

Что собираем, где храним, как защищаем. Данные пилота хранятся **отдельно** от синтетических
данных стенда валидации; в каждой таблице есть поле `source = pilot`, чтобы выгрузки нельзя было
смешать. Юридическая сторона (обработка персональных данных) требует проверки юристом — см.
[чек-лист](launch-checklist.md#согласия-и-право).

## Принципы

1. **Минимум.** Собираем только то, что нужно для пяти критериев и для плана валидации.
2. **Псевдонимы.** В таблицах результатов — `pid` (случайная строка), без ФИО и email.
   Таблица соответствия `pid` ↔ участник хранится отдельно, доступ у одного человека в команде.
3. **Не перепродаём и не обучаем.** Данные пилота не уходят во внешние API и не используются для
   обучения моделей без нового согласия. Пилотные ответы на задания могут калибровать банк
   платформы штатно; включать ли это для пилота — решение до старта
   ([чек-лист](launch-checklist.md#стенд)).
4. **Не измеряем лишнего.** Пол, возраст, вуз в таблицы не пишем и в модели не используем
   ([механики, §17](../mechanics.md#17-защищённые-признаки)).
5. **Нет данных — нет значения.** Пропуски остаются пропусками; не заполняются и не
   импутируются.

## Таблицы

Хранение — таблицы в закрытом хранилище команды (CSV/SQLite); для платформенных данных —
выгрузка из базы стенда.

### participants

| Поле | Тип | Что |
|---|---|---|
| `pid` | строка | псевдоним |
| `role` | перечисление | candidate / employer / expert |
| `consent_version`, `consent_at` | строка, дата | версия и момент согласия |
| `consent_flags` | набор | участие / показ профиля работодателям / цитирование / хранение дольше срока |
| `withdrawn_at` | дата или пусто | момент отзыва согласия |
| `recruit_channel` | строка | как нашли участника (для оценки смещения набора) |

### candidates (профиль участника, без идентифицирующих данных)

| Поле | Что |
|---|---|
| `pid` | ссылка |
| `declared_grade` | заявленный грейд |
| `years_experience_band` | стаж диапазоном: 0–1 / 1–3 / 3–6 / 6+ |
| `has_fsp_history` | да / нет |
| `stack_tags` | технологии из анкеты |
| `work_formats`, `city_region` | формат; регион, не город (при малой выборке город идентифицирует) |

### test_attempts (из базы платформы)

| Поле | Что |
|---|---|
| `attempt_id`, `pid`, `attempt_no` | 1 — первое, 2 — повтор |
| `started_at`, `finished_at`, `status` | completed / abandoned / expired |
| `items_shown`, `duration_sec` | число заданий, время |
| `theta_mean`, `theta_sd` | оценка и погрешность |
| `category_grade` | присвоенный грейд или «без категории» |
| `grade_probs` | вероятности грейдов |
| `build_hash` | хэш коммита стенда |

### item_responses (для M11)

`attempt_id`, `family_id`, `item_instance_id`, `correct`, `latency_sec`. Текст ответа кандидата не
хранится, если он не нужен для проверки эталона; в таблице — только верность.

### needs

`need_id`, `employer_pid`, `text_hash` (сам текст — в закрытом хранилище команды), `parsed_fields`,
`parse_edits` (число правок), `salary_from`, `salary_to`, `salary_basis` = «gross, RUB/мес».

### shortlist_rows

`need_id`, `candidate_pid`, `rank`, `block` (точный грейд / близкие / не подтверждён),
`score_S`, `p_accept`, `in_top8`, `is_random_control`. Эти поля **недоступны экспертам**.

### expert_ratings

`need_id`, `candidate_pid`, `expert_pid`, `score_0_3`, `reason`, `seconds_spent`, `rated_at`.

### employer_card_ratings

`need_id`, `candidate_pid`, `card_useful_0_3`, `card_would_invite`, `card_explain`.

### employer_time

`need_id`, `t_start_describe`, `t_shortlist_ready`, `t_decision`, `t_first_invite`, `self_time_min`,
`baseline_minutes`.

### invitations

`invite_id`, `need_id`, `candidate_pid`, `salary_from`, `salary_to`, `sent_at`, `status`
(sent / viewed / accepted / declined / expired), `responded_at`, `decision_reason`, `would_same`.

### feedback_*

По одной таблице на форму из [feedback-form.md](feedback-form.md); столбцы — имена полей в
скобках. Свободные тексты — в отдельном столбце, без правки.

### incident_log

`at`, `kind` (сбой стенда / ошибка данных / обращение участника), `affects` (какие записи),
`resolution`. Записи, затронутые сбоем, помечаются и исключаются из расчётов в отчёте с указанием
числа исключённых.

## Что не хранится

ФИО, email и телефон — только в таблице соответствия. Пароли, токены, тексты переписки после
принятия приглашения — в таблицы пилота не попадают. Ожидаемая зарплата кандидата в аналитике
пилота не нужна и не выгружается ([механики, §14](../mechanics.md#14-рынок)).

## Согласие

Подписывается до первого действия на стенде, отдельно для каждой роли. В согласии, простым
языком:

- кто проводит пилот, цель, что пилот исследовательский и **результатов найма не гарантирует**;
- какие данные собираются (перечень выше) и зачем, что они обезличиваются псевдонимом;
- что работодатель видит обезличенную карточку до принятия приглашения, а контакты — только
  после; что кандидат вправе отклонить любое приглашение без объяснений;
- что данные не передаются внешним сервисам и обрабатываются в закрытом контуре команды;
- срок хранения и способ удаления: данные удаляются или необратимо обезличиваются не позже
  срока после закрытия пилота; **срок и правовое основание определяют перед стартом
  ([чек-лист](launch-checklist.md#согласия-и-право))**;
- право отозвать согласие в любой момент: данные участника исключаются из последующих расчётов;
  уже опубликованные агрегаты пересчитываются по возможности;
- отдельный флаг на цитирование свободных ответов;
- контакт ответственного за данные.

Для работодателей: соглашение о том, что персональные данные кандидатов из пилота они не
выгружают и не используют вне пилота; для экспертов: что оценки анонимны для работодателей, а
карточки конфиденциальны.

Текст согласия пишет и согласует ответственный за данные вместе с юристом; в репо хранится его
версия и номер, но не подписанные экземпляры.

## Контроль качества данных

Перед расчётом: проверка полноты по каждой таблице, дубликатов `pid`, соответствия числа пар
плану ([рубрика](rubric.md#выборка-пар)), совпадения `build_hash` по всем попыткам; расхождения
фиксируются в `incident_log`. Расчёт критериев запускается скриптом, написанным **до** получения
данных и заморозенным в репо вместе с порогами; пилотные таблицы в репо не коммитятся.
