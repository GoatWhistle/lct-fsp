# Понимание текста — за портом `TextUnderstanding`

Свободный текст превращается в структуру через порт `TextUnderstanding` в `usecase/interface.py`.
Входов два: потребность, которую работодатель написал как есть (`docs/mechanics.md`, §12), и
резюме из PDF (§16). Выход — черновик потребности или анкеты. Черновик показывается на экране
«система поняла так» и сохраняется только после того, как человек его проверил.

## Контракт

- **Вход — очищенный текст.** Скрытый текст PDF (белый, нулевого размера, за полями страницы)
  убирается до порта, адаптер его не видит.
- **Выход — только значения справочника:** специализация, грейд, формат работы, технологии,
  сферы бизнеса, темы и их важность; вилка — числами. Сценарий не доверяет адаптеру и сам
  отбрасывает всё, чего нет в справочнике.
- **У поля — уверенность** в [0, 1] или `None`, если адаптер её не считает. Неуверенное поле
  подсвечивается на экране правки; на скор уверенность не влияет.
- **Вне справочника** — отдельный результат: такой специализации нет и ближайшие специализации
  из справочника, а не пустой черновик.
- **ФИО и контакты** из резюме достают правила; модели отвечают на вопросы о стеке, грейде,
  ролях и софт-скиллах.
- **Порт ничего не оценивает.** Требования по темам из черновика потребности считает домен
  (§12). Распознанное из резюме попадает только в самоописание — низший уровень доверия с
  потолком вклада $\lambda$ — и на категорию не влияет.
- **Наружу — ни одного сетевого вызова.** Модель — локальные веса или локальный сервис в
  compose.

## Реализации

- **Правила и словарь синонимов** — вариант по умолчанию и запасной путь: когда модели нет, она
  ошиблась или не уложилась в таймаут из конфига.
- **Локальная LLM** — `llama-server` из llama.cpp, отдельный контейнер в compose: российская
  модель в GGUF на CPU. Ответ ограничен JSON-схемой черновика со значениями справочника на
  уровне декодирования, дальше та же проверка кодом. Модель и таймаут — из конфига.
  Контейнер — в сети compose без выхода наружу, под своим profile: без него бэкенд стартует и
  отвечает правилами. Сбой, нечитаемый ответ и таймаут — откат на правила в том же запросе.

Модельный адаптер становится вариантом по умолчанию, только если по точности по полям на
отложенной размеченной выборке выигрывает у правил (`docs/validation-plan.md`). Размеченная
выборка — только для проверки и калибровки, не для обучения: иначе валидация замкнута на себя.

**Сейчас по умолчанию — правила.** llama на D5 не замерена — модель для стенда жюри выбирается
по его ресурсам, — и включается только конфигом: `TEXT_UNDERSTANDING=llama` и profile `llama`
в compose. Ответы модели для M21 стенд записывает и пересобирает отчёт из записи без сети
(`validation/data/need_texts.md`).

## Почему так

- **Через порт кандидат ничего не накручивает.** Потребность пишет работодатель. Резюме даёт
  только самоописание, которое кандидат сам подтверждает; инъекция в резюме максимум испортит
  предзаполнение его же формы. LLM не выведет значение вне справочника: схема ограничивает
  ответ, а значения проверяет код.
- **Стенд жюри — CPU и без гарантии сети.** Запасной путь на правилах обязателен, а модель
  должна меняться без правки сценариев.

## Рассмотренные варианты

- **LLM прямо в сценарии разбора:** отклонено. Вывод свободный, запасного пути нет, смена
  модели правит сценарий и тесты.
- **Внешний API модели:** отклонено. Резюме — персональные данные, а они во внешние API не
  уходят (§16). Сети на стенде жюри может не быть.
- **Модель решений** — негенеративная модель с ответами из закрытого списка: отклонено. Без
  дообучения отвечает около случайного, а данных для дообучения нет, кроме своей же синтетики.
- **Отдельный порт на резюме и на потребность:** отклонено. Справочник, проверка вывода и
  запасной путь у них общие; один порт с двумя операциями.

## Вне порта

- **Пересказ посчитанных цифр словами** — объяснение подборки, план для кандидата — обратное
  направление: структура → текст. Когда появится, это свой порт с тем же правилом: числа и темы
  в тексте сверяет код, а при расхождении показываются данные без текста.
- **Черновики шаблонов заданий** — офлайн, вне приложения, с ревью человеком (§5).
- **Базовые линии стенда валидации** через этот порт не ходят, прод-сценарии их не импортируют
  (ADR 0001).

## Следствия

- Порт появляется в коде вместе с первым сценарием разбора. Черновики потребности и анкеты —
  доменные типы; адаптер выбирается из конфига и собирается в `backend/main.py`.
- Каждый адаптер проходит одни и те же тесты: вывод не выходит за справочник, наружу нет
  сетевых вызовов, инструкция в тексте не меняет выдачу.
- Сравнение адаптеров по точности по полям и по времени ответа на CPU — в отчёте стенда
  валидации.
