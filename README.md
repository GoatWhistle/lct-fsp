# Подбор ИТ-специалистов ФСП

Платформа подбора с обратной механикой: кандидат проходит опрос и адаптивный тест и получает
профиль навыков и категорию, работодатель описывает потребность, получает подборку с объяснением
и сам приглашает кандидата. Достижения ФСП — самый весомый сигнал профиля.

## Запуск

Нужен Docker с Compose v2. Из корня репо:

```sh
docker compose up --build
```

Когда стенд поднимется:

| Что | Адрес |
|---|---|
| Фронт | http://localhost:3000 |
| Swagger (OpenAPI) | http://localhost:8000/api/docs |
| Mailpit — письма подтверждения | http://localhost:8025 |
| Keycloak, изображает ФСП ID (админка `admin` / `admin`) | http://localhost:8080 |

Путь для проверки: «Регистрация» → выбрать роль → письмо приходит в Mailpit → ссылка из письма
→ «Войти» → кабинет своей роли. Без подтверждения адреса вход закрыт.

Кандидат входит и через ФСП ID: «Войти через ФСП ID» на странице входа → страница ФСП ID →
тестовый участник → кабинет кандидата, достижения ФСП уже в профиле. Новый участник получает
учётку кандидата; если учётка с его email уже есть, вход отклоняется — войдите по email и
привяжите ФСП ID в профиле кандидата («ФСП ID» → «Привязать ФСП ID»). Тестовые участники — пароль
`fsp-demo-2026`:

| Логин ФСП ID | Что в реестре |
|---|---|
| `fsp-winner` | победитель и призёр по алгоритмам, финал по продуктовому |
| `fsp-prize` | призёр хакатона в роли бэкенда, финал по алгоритмам |
| `fsp-finalist` | только финалы |
| `fsp-qualifier` | только отборы — факт в профиле, не наблюдение |
| `fsp-no-history` | без истории ФСП |
| `fsp-team-frontend`, `fsp-team-data`, `fsp-team-qa`, `fsp-team-devops` | командные результаты с ролью |
| `fsp-security` | победитель и призёр по информационной безопасности |
| `fsp-robotics` | дисциплины без тем — только факт |
| `fsp-divergent-algo`, `fsp-divergent-product` | сильные результаты: пройдите тест слабо — увидите расхождение |
| `fsp-unverified` | email в ФСП ID не подтверждён — вход отклоняется |
| `demo-<специализация>-<грейд>` | привязаны к демо-кандидатам с ФСП, см. «Демо-данные» |

Достижения ФСП — наблюдения высшего уровня доверия в профиле навыков: в объяснении подборки у
темы появляется «подтверждено ФСП». Работодатель в обезличенной карточке видит тип результата,
дисциплину и год, PDF-профиль — достижения полностью. Грейд и категорию ФСП не меняет. Keycloak на
старте занимает около 0,5 ГБ памяти (лимит контейнера — 768 МБ); вход по email без него работает.

### Демо-данные

Чистый стенд засевается одной командой — после `docker compose up`:

```sh
docker compose exec backend python seed_demo.py
```

Засев идёт через те же сценарии, что HTTP: регистрация и подтверждение адреса, опрос, тест,
анкета, привязка ФСП ID, компания и потребности. Повторный запуск ничего не дублирует и
продолжает прерванный. Данные синтетические. Пароль всех демо-учёток — `demo-2026`:

| Учётка | Роль | Что в ней |
|---|---|---|
| `employer@demo.example` | работодатель | «Демо-Технологии», финтех, вилки по рынку: потребности middle бэкенд, фронтенд и данные, junior QA, senior DevOps |
| `employer-2@demo.example` | работодатель | «Демо-Ритейл», e-commerce, вилки ниже рынка: junior и senior бэкенд, стажёр фронтенд, middle QA, senior данные |
| `<специализация>-<грейд>@demo.example` | кандидат | категория «специализация × грейд», без истории ФСП |
| `<специализация>-<грейд>-fsp@demo.example` | кандидат | та же категория, привязан ФСП ID `demo-<специализация>-<грейд>` |

Специализации — `backend`, `frontend`, `data-ml`, `qa`, `devops`, грейды — `intern`, `junior`,
`middle`, `senior`: всего 40 кандидатов, например `backend-middle@demo.example`. Кандидат
проходит тест сам, по модели ответа стенда валидации; если тест дал ему другую категорию, засев
берёт следующего — `<специализация>-<грейд>-2@demo.example`, `-3`. Итоговый список с
категориями печатает команда засева. Кандидат с ФСП входит и через ФСП ID под
`demo-<специализация>-<грейд>` с паролем `fsp-demo-2026`.

Кандидат без категории попадает на путь к ней: опрос (направление — специализация) → выбор
грейда → тест → результат — уровень с погрешностью, вероятность каждого грейда, категория и
профиль навыков по темам. Тест адаптивный и готов для всех специализаций: следующее задание выбирается
по текущей оценке уровня, тест останавливается, когда уровень определён с нужной точностью, —
у каждого кандидата свой набор заданий и свои экземпляры.

Кандидат в любой момент, кроме самого теста, заполняет профиль: ФИО, контакты, роли, стаж,
стек из справочника с автодополнением, софт-скиллы, ожидания: формат, город, зарплата и, по
желанию, интересные сферы бизнеса, — и карточку опыта: места работы и проекты с периодами и
технологиями, годы по технологиям считаются из них. Карточка — со слов кандидата: на подбор,
уровень и категорию не влияет. Профиль можно заполнить по резюме: «Заполнить по резюме» → PDF →
распознанное подставляется в форму, неуверенное выделено, сохраняет кандидат сам. Разбор
локальный, файл не сохраняется, текст, которого не видно на странице, не читается. По стажу и
ролям профиля шаг выбора грейда показывает подсказку — выбирает грейд кандидат. Все суммы на платформе — в месяц до вычета НДФЛ, так и
подписаны. «Скачать PDF» собирает профиль единого вида: категория и профиль навыков, если тест
пройден, и самоописание. Работодатель видит кандидата обезличенной карточкой — без ФИО, контактов,
свободного текста («о себе», роли, софт-скиллы, карточка опыта) и ожидаемой зарплаты.

Работодатель заполняет профиль компании (название, сфера деятельности, описание, контакты) и
заводит потребности: кого ищет, чем занимается команда, специализация, грейд, стек, формат, город и
вилка. Важность тем выводится из стека прямо в форме, её можно поправить.

Потребность можно описать словами: «Описать словами» в кабинете → текст вакансии как есть →
экран «система поняла так» с полями формы, где выделено, в чём система не уверена и чего не
нашла. После правки — «Сформировать подборку» без сохранения или «Сохранить как потребность».
Разбор локальный, на правилах и словаре синонимов `config/synonyms.yaml`; текст никуда не
уходит. Специализации вне справочника (1С, геймдев) получают честный ответ и ближайшие
специализации кнопками.

Вместо правил разбирать может локальная модель — `llama-server` из llama.cpp на CPU, в отдельной
сети compose без выхода наружу. По умолчанию она выключена: на D5 замерены только правила, а
модель становится вариантом по умолчанию только по замеру
([ADR 0002](docs/adr/0002-text-understanding-port.md)). Включение — файл модели GGUF в `models/`
и

```sh
LLAMA_MODEL_FILE=<файл>.gguf TEXT_UNDERSTANDING=llama docker compose --profile llama up --build
```

Модель отвечает только значениями справочника; не ответила за `TEXT_UNDERSTANDING_TIMEOUT_SECONDS`
или ответила сбоем — разбор отвечает правилами, интерфейс разницы не показывает.

В карточке потребности — «Сформировать подборку»: кандидаты с категорией потребности, затем
«близкие» соседнего грейда, по убыванию соответствия. У каждого — соответствие и его объяснение:
вклад каждой темы и самоописанного стека, сумма вкладов равна соответствию. Карточка кандидата
обезличена. Подборка сохраняется и открывается позже с той же выдачей; «Перестроить» создаёт
новую по текущим данным.

Вакансии — дополнительный сценарий: работодатель публикует вакансию с обязательной вилкой,
правит её и снимает с публикации, кандидат — и без категории — видит общий список и
откликается сам. Отклик сразу открывает компании вакансии имя, контакты и профиль кандидата,
бюджет приглашений не тратит; принимает или отклоняет его работодатель, статус видят обе
стороны.

Порты, секрет подписи входа и адрес и ключи ФСП ID меняются в `.env` — образец в
[`.env.example`](.env.example). Настоящий ФСП ID — смена `FSP_ID_ISSUER`, `FSP_ID_SERVER_URL`,
`FSP_ID_CLIENT_ID` и `FSP_ID_CLIENT_SECRET`, без правки кода.

## Тесты

```sh
docker compose run --rm --build tests
```

Контейнер гоняет весь набор. Тесты трёх уровней — маркеры pytest, правило разметки — в
`backend/tests/conftest.py`:

- `unit` — без базы и долгих прогонов; `uv run pytest` без флагов гоняет только их;
- `integration` — ходят в бэкенд через HTTP API или в хранилище напрямую; на сервере PostgreSQL
  создаётся временная база и удаляется после прогона;
- `simulation` — свойства механик на синтетике: сходимость калибровки, потолок показов, точность
  адаптивного теста.

Без Docker Compose, с [uv](https://docs.astral.sh/uv/) и Docker, из `backend/`: `uv run pytest`
— unit, `uv run pytest -m integration` — PostgreSQL поднимется в контейнере сам,
`uv run pytest -m simulation`, весь набор — `uv run pytest -m ""`.

Стенд валидации — синтетические кандидаты с известной истиной проходят те же сценарии теста и
калибровки, что HTTP, на in-memory хранилищах. Команды из `backend/`:

- `uv run python -m validation` (или `report`) — отчёт валидации одной командой: D1 и D2 по
  сидам плана проходят тест, повтор, наивный тест B0 и подборку, отчёт с вердиктом по каждой
  метрике плана пишется в [`docs/validation-report.md`](docs/validation-report.md), картинки —
  рядом, в `docs/validation-report/`. Тот же прогон — тот же файл байт в байт; полный прогон
  идёт в пуле процессов десятки минут, `--candidates`, `--pairs`, `--warm`, `--compare` и
  `--report` — для короткого прогона в другой файл;
- `uv run python -m validation honesty` — честность погрешности уровня и стабильность грейда на
  прогретом банке D1 (`--seed`, `--candidates`, `--pairs`);
- `uv run python -m validation tune` — подбор поправки погрешности `level_sd_inflation` на
  настроечном наборе D3;
- `uv run python -m validation fit` — подбор проверки согласия семейства с моделью `item_fit_*`
  на D3: пять гипотез на банке с испорченными семействами (`--seed`, `--warm`), около часа;
- `uv run python -m validation parsing` — M21, точность разбора потребности из текста по полям на
  размеченном наборе D5 (`--dataset` — другой файл того же формата,
  `validation/data/need_texts.md`); `--model <имя>` — разбор моделью из записи её ответов, без
  сети, `--record N` — сначала дописать в запись недостающие ответы в N потоков;
- `uv run python -m validation market` — синтетический рынок D1 файлами в
  `validation/data/market/d1` (`--set d2` — набор со сдвигом D2, `--seed`, `--candidates` — на
  специализацию, `--out`): истина в `truth/`, наблюдаемое в `observed/`, потребности,
  работодатели и эталон пар `pairs.jsonl`. Тот же seed — те же файлы байт в байт, в репо они не
  хранятся;
- `uv run python -m validation acceptance` — обучение модели принятия на своём сиде: набор с
  параметрами D1 проходит тест и подборки, синтетические кандидаты решают по приглашениям, CatBoost
  учится на 20 000 пар. Пишет `app/adapter/acceptance_model.cbm` — его загружает прод — и базовые
  линии M7 в `validation/data/acceptance_baselines.json`; оба файла в репо. Только CPU, около
  шести минут; тот же сид — тот же файл модели байт в байт.

Банк заданий — тоже из `backend/`:

- `uv run python -m bank_report` — отчёт покрытия в markdown: доля трассировки по темам,
  сценарные семейства у middle и senior, ячейки «тема × грейд» без семейств и без описания в
  матрице грейдов; с `--calibration` — и сверка сложности с экспертной по калибровке из базы;
- `uv run python -m bank_report matrix` — пересобрать [`docs/grade-matrix.md`](docs/grade-matrix.md)
  из `config/grade_matrix.yaml`.

## Устройство

```
backend/                 FastAPI + SQLAlchemy + Alembic, PostgreSQL
  main.py                сборка прода вручную: `create_app` (запуск — `uvicorn --factory
                         main:create_app`) и синхронизация справочника `sync_catalog`
  composition.py         общая проводка сценариев из портов — для прода и стенда
  settings.py            настройки окружения `Settings` и параметры механик `Mechanics`
  fsp_stub.py            генератор заглушки ФСП: realm Keycloak и реестр достижений из одного seed
  seed_demo.py           демо-засев стенда через прод-сценарии
  validation/            стенд валидации: сборка `main.py`, синтетика, команды
  app/                   только слои — docs/adr/0001-layers-and-ports.md
    domain/              сущности и правила без библиотек: тест, категория, профиль навыков,
                         подборка, учётки, справочники; банк семейств — domain/bank/
    usecase/             сценарии на единице работы и порты (`interface.py`)
    controller/          роутеры FastAPI, схемы Pydantic, зависимости, guard ролей
    adapter/             реализации портов: модель навыка IRT, выбор задания, калибровка,
                         почта, PDF, пароли, токен входа, файл справочника, ФСП ID (OIDC),
                         реестр ФСП, разбор текста на правилах и моделью (llama.cpp), видимый
                         текст PDF резюме
    repository/          хранилища на Postgres, ORM всех таблиц (`orm/`), in-memory (`memory/`)
  config/mechanics.yaml  параметры механик — те же, что в docs/parameters.md
  config/catalog.yaml    справочники: грейды, сферы бизнеса, специализации, темы, технологии,
                         дисциплины ФСП
  config/synonyms.yaml   словарь синонимов для разбора потребности и резюме из текста
  config/fsp_registry.json  заглушка реестра ФСП — генерирует fsp_stub.py
  migrations/            миграции схемы
  tests/                 тесты через HTTP API и сценарии на in-memory хранилищах
frontend/                React + TypeScript (Vite), на стенде — nginx
keycloak/                realm, который изображает ФСП ID, — генерирует backend/fsp_stub.py
docker-compose.yml       PostgreSQL, бэкенд, фронт, Mailpit, Keycloak; llama-server — profile llama
```

Зависимости слоёв идут внутрь, к `domain`; `tests/test_layers.py` это проверяет. Сущность
проходит все слои под одним именем: учётки — `domain/account.py`, `usecase/account.py`,
`controller/auth.py`, `repository/account.py`; потребность — `need.py` в каждом слое; путь
кандидата к категории — `domain/attempt.py`, `usecase/attempt.py`, `controller/path.py`,
`repository/attempt.py`; подборка — `selection.py`, P(принятия) — за портом `AcceptanceModel`;
регулярные задания — `regular_task.py` в каждом слое, свежесть профиля — `ProfileFreshness` в
`usecase/skill_profile.py`; приглашение — `invitation.py` в каждом слое, статус «истекло» выводит
домен при чтении.
Вход — по email и паролю или через ФСП ID (`controller/fsp.py`, сценарии — `usecase/fsp.py`),
пароль хранится хэшем argon2, сессия — подписанный токен в httpOnly-cookie. Права проверяет
бэкенд: разделы `/api/candidate/*` и `/api/employer/*`
отвечают 403 чужой роли.

## Разработка

Бэкенд локально — база, почта и ФСП ID из compose, код с перезагрузкой (бэкенд вне compose ходит
в Keycloak по `localhost:8080` — адрес по умолчанию):

```sh
docker compose up -d db mailpit keycloak
cd backend
uv sync
uv run alembic upgrade head
uv run python -c 'import main; main.sync_catalog()'
uv run uvicorn --factory main:create_app --reload
```

Фронт локально — `cd frontend && npm install && npm run dev`, http://localhost:3000, запросы
`/api` проксируются на `:8000`.

Заглушка ФСП — синтетика: персоны тестовых участников в `backend/fsp_stub.py`, после правки —
`cd backend && uv run python fsp_stub.py` перезапишет `keycloak/realm-fsp-id.json` и
`backend/config/fsp_registry.json`. Realm импортируется при первом старте Keycloak; чтобы
перечитать — `docker compose up -d --force-recreate keycloak`.

Проверки перед PR:

```sh
cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy . && uv run pytest -m ""
cd frontend && npm run lint && npm run build
```

### Образцы

- **Новая сущность** — по слоям, файлы под одним именем
  ([`docs/adr/0001-layers-and-ports.md`](docs/adr/0001-layers-and-ports.md)):
  1. `app/domain/<имя>.py` — dataclass-ы и правила без SQLAlchemy, Pydantic и FastAPI;
  2. `app/usecase/<имя>.py` — сценарий-класс на единице работы, каждый вызов — блок
     `with uow:`; хранилище — порт-`Protocol` в `app/usecase/interface.py`;
  3. `app/repository/<имя>.py` — реализация порта, ORM таблицы — `app/repository/orm/<имя>.py`
     и импорт в `app/repository/orm/__init__.py` (по нему миграции видят таблицы); наружу —
     доменные значения, не строки ORM;
  4. `app/controller/<имя>.py` и `<имя>_schemas.py` — роутер и схемы; сценарий приходит
     зависимостью из `app/controller/deps.py`;
  5. проводка — фабрика сценария в `backend/composition.py`, реализации — в `create_app`
     (`backend/main.py`), там же подключается роутер.
- **Миграция** — `uv run alembic revision --autogenerate -m "short english slug"`, затем
  прочитать и поправить. Тест `test_models_match_migrations` падает, если модели разошлись с
  миграциями. Если после слияния веток у миграций две головы — `uv run alembic merge heads`.
- **Подключение к базе** — движок только через `create_db_engine`
  (`app/repository/database.py`): время из базы приходит в UTC при любом часовом поясе
  сервера. Временная база тестов — в `Europe/Moscow`, поэтому время, зависящее от пояса базы,
  роняет тесты.
- **Справочники** — данные в `backend/config/catalog.yaml`, не в коде. Бэкенд при старте
  синхронизирует их с базой (`sync_catalog` в `backend/main.py`, та же команда — из
  «Разработки»); коды стабильны — на них ссылаются тест, профиль и подбор.
- **Параметры механик** — числа из [`docs/parameters.md`](docs/parameters.md) под теми же
  именами в `config/mechanics.yaml` и полях `Mechanics` (`backend/settings.py`); в эндпоинт
  приходят через `MechanicsDep`. Константами в коде не пишутся. Новый параметр или значение — в
  доке и конфиге одним PR: `test_mechanics_config.py` сверяет их.
- **Ошибки** — подкласс `DomainError` в `app/domain/errors.py` с `code` и `message`
  по-русски, без HTTP-статуса. Статус — строка в `STATUS` (`app/controller/errors.py`);
  эндпоинт перечисляет ошибки в `responses=error_responses(...)`, и коды попадают в OpenAPI.
- **Разделы роли** — роутер с префиксом `/api/candidate` или `/api/employer`,
  `dependencies=role_guard(Role.…)` и `responses=ROLE_RESPONSES` (см.
  `app/controller/cabinets.py`).
- **Порт внешней системы** — по образцу почты, правило —
  [`docs/adr/0001-layers-and-ports.md`](docs/adr/0001-layers-and-ports.md):
  1. порт — `Protocol` в `app/usecase/interface.py` (`Mailer`); на входе и выходе только типы из
     `app/domain` (`Mail` в `app/domain/mail.py`), без ORM, Pydantic и типов библиотеки;
  2. реализация — в `app/adapter/` (`SmtpMailer` в `app/adapter/mail.py`); библиотеку и протокол
     системы импортирует только она — `test_layers.py` это проверяет для SMTP и fpdf2;
  3. сборка — в `create_app` (`backend/main.py`): адаптер создаётся там и передаётся в
     проводку `composition.py`, она отдаёт его сценарию (`Accounts` шлёт письмо подтверждения);
  4. тестовая реализация — тоже в `app/adapter/` (`MemoryMailer`); тесты подставляют её через
     параметр `create_app`, хелперы поверх — в `tests/conftest.py` (`Outbox`).
- **Тест** — через HTTP API, фикстуры из `tests/conftest.py`: `client` — аноним,
  `signed_in(Role.candidate)` — вошедший пользователь роли, `outbox` — отправленные письма,
  `fsp_id` — ФСП ID в памяти (код за участника — `issue`), `fsp_registry` — реестр ФСП в памяти.
- **Типы API на фронте** генерируются из OpenAPI: при запущенном бэкенде `npm run api:types`.
