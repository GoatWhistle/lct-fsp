# Запуск и проверки

Пошагово: как поднять стенд, засеять демо-данные, войти через ФСП ID, прогнать тесты и стенд
валидации и разрабатывать локально. Что делает продукт — [README](../README.md), как устроен код
— [архитектура](architecture.md).

## Требования

| Что | Версия | Зачем |
|---|---|---|
| Docker с Compose v2 | любая актуальная | стенд целиком: PostgreSQL, бэкенд, фронт, Mailpit, Keycloak |
| [uv](https://docs.astral.sh/uv/) | 0.9 и новее | бэкенд и стенд валидации вне Docker, Python 3.12 ставится сам |
| Node.js | 22.18 и новее | фронт вне Docker |

Память стенда в покое — около 0,8 ГБ: Keycloak 0,55 ГБ (лимит контейнера 768 МБ), бэкенд
0,2 ГБ, остальное меньше 50 МБ на контейнер. Локальная модель llama.cpp включается отдельно и
требует ещё до 16 ГБ.

## Стенд в Docker Compose

Из корня репо:

```bash
docker compose up --build
```

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:3000 |
| Swagger (OpenAPI) | http://localhost:8000/api/docs |
| Mailpit — письма подтверждения | http://localhost:8025 |
| Keycloak, изображает ФСП ID (админка `admin` / `admin`) | http://localhost:8080 |

Путь для проверки: «Регистрация» → выбрать роль → письмо приходит в Mailpit → ссылка из письма
→ «Войти» → кабинет своей роли. Без подтверждения адреса вход закрыт.

Порты, секрет подписи входа, адрес и ключи ФСП ID меняются в `.env` — образец в
[`.env.example`](../.env.example). Без `.env` стенд стартует на значениях по умолчанию.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `SECRET_KEY` | `dev-only-…` | подпись токена входа; на общем стенде — своя, `openssl rand -hex 32` |
| `FRONTEND_URL` | `http://localhost:3000` | адрес фронта в ссылке из письма и возврат из ФСП ID |
| `COOKIE_SECURE` | `false` | `true` — cookie входа только по HTTPS |
| `SESSION_COOKIE_NAME` | `calibr_session` | имя cookie входа: cookie не изолируются по порту, и на localhost чужое приложение с тем же именем (например `access_token`) затирало бы сессию |
| `SESSION_TTL_HOURS` | `168` | срок входа; cookie и токен живут ровно столько, продления при активности нет — по истечении нужен новый вход |
| `FSP_ID_ISSUER`, `FSP_ID_SERVER_URL` | локальный Keycloak | публичный адрес realm ФСП ID и адрес для бэкенда |
| `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET` | `lct-platform`, `dev-only-…` | клиент платформы в ФСП ID |
| `FSP_REGISTRY_PATH` | `backend/config/fsp_registry.json` | заглушка реестра достижений |
| `DEMO_MODE` | `false` | режим жюри: демо-вход работодателя, новый тестовый кандидат и экспресс-тест ([механики, §18](mechanics.md#18-режим-жюри)); выключенный ничего не открывает |
| `TEXT_UNDERSTANDING` | `rules` | разбор текста: `rules` или `llama` |
| `FRONTEND_PORT`, `BACKEND_PORT`, `POSTGRES_PORT`, `MAILPIT_UI_PORT`, `KEYCLOAK_PORT` | 3000, 8000, 5432, 8025, 8080 | порты на хосте |

## Демо-данные

Чистый стенд засевается одной командой после `docker compose up`:

```bash
docker compose exec backend python seed_demo.py
```

Засев идёт через те же сценарии, что HTTP: регистрация и подтверждение адреса, опрос, тест,
анкета, привязка ФСП ID, компания и потребности. Повторный запуск ничего не дублирует и
продолжает прерванный. Данные синтетические. Пароль всех демо-учёток — `demo-2026`.

| Учётка | Роль | Что в ней |
|---|---|---|
| `employer@demo.example` | работодатель | «Демо-Технологии», финтех, вилки по рынку: потребности middle бэкенд, фронтенд и данные, junior QA, senior DevOps |
| `employer-2@demo.example` | работодатель | «Демо-Ритейл», e-commerce, вилки ниже рынка: junior и senior бэкенд, стажёр фронтенд, middle QA, senior данные |
| `<специализация>-<грейд>@demo.example` | кандидат | категория «специализация × грейд», без истории ФСП |
| `<специализация>-<грейд>-fsp@demo.example` | кандидат | та же категория, привязан ФСП ID `demo-<специализация>-<грейд>` |

Специализации — `backend`, `frontend`, `data-ml`, `qa`, `devops`, грейды — `intern`, `junior`,
`middle`, `senior`: всего 40 кандидатов, например `backend-middle@demo.example`. Кандидат
проходит тест сам, по модели ответа стенда валидации; если тест дал ему другую категорию, засев
берёт следующего — `<специализация>-<грейд>-2@demo.example`, `-3`. Итоговый список с
категориями печатает команда засева.

Приглашений, откликов, вакансий и регулярных заданий засев не создаёт: их проще показать вживую
— пригласить кандидата из подборки, опубликовать вакансию и откликнуться на неё.

## Вход через ФСП ID

«Войти через ФСП ID» на странице входа → страница ФСП ID → тестовый участник → кабинет
кандидата, достижения ФСП уже в профиле. Новый участник получает учётку кандидата; если учётка с
его email уже есть, вход отклоняется — войдите по email и привяжите ФСП ID в профиле кандидата
(«ФСП ID» → «Привязать ФСП ID»). Пароль тестовых участников — `fsp-demo-2026`.

| Логин ФСП ID | Что в реестре |
|---|---|
| `fsp-winner` | победитель и призёр по алгоритмам, финал по продуктовому |
| `fsp-prize` | призёр хакатона в роли бэкенда, финал по алгоритмам |
| `fsp-finalist` | только финалы |
| `fsp-qualifier` | только отборы — факт в профиле, не наблюдение |
| `fsp-no-history` | без истории ФСП |
| `fsp-team-frontend`, `fsp-team-data`, `fsp-team-qa`, `fsp-team-devops` | командные результаты с ролью |
| `fsp-security` | победитель и призёр по информационной безопасности |
| `fsp-robotics` | дисциплины без тем — только факт |
| `fsp-divergent-algo`, `fsp-divergent-product` | сильные результаты: пройдите тест слабо — увидите расхождение |
| `fsp-unverified` | email в ФСП ID не подтверждён — вход отклоняется |
| `demo-<специализация>-<грейд>` | привязаны к демо-кандидатам с ФСП |

Достижения ФСП — наблюдения высшего уровня доверия в профиле навыков: в объяснении подборки у
темы появляется «подтверждено ФСП». Работодатель в обезличенной карточке видит тип результата,
дисциплину и год, PDF-профиль — достижения полностью. Грейд и категорию ФСП не меняет. Keycloak
стартует около минуты; вход по email без него работает. Как это устроено и что меняется при
переходе на настоящий ФСП ID — [интеграция с ФСП](fsp-integration.md).

## Локальная модель для разбора текста

По умолчанию потребность и резюме разбираются правилами и словарём синонимов
`backend/config/synonyms.yaml`. Вместо правил может разбирать локальная модель — `llama-server`
из llama.cpp на CPU, в отдельной сети compose без выхода наружу. Включение — файл модели GGUF в
`models/` и

```bash
LLAMA_MODEL_FILE=<файл>.gguf TEXT_UNDERSTANDING=llama docker compose --profile llama up --build
```

Модель отвечает только значениями справочника; не ответила за
`TEXT_UNDERSTANDING_TIMEOUT_SECONDS` или ответила сбоем — разбор отвечает правилами, интерфейс
разницы не показывает. Почему по умолчанию правила — [ADR 0002](adr/0002-text-understanding-port.md).

## Тесты

Весь набор бэкенда — в контейнере:

```bash
docker compose run --rm --build tests
```

Тесты трёх уровней — маркеры pytest, правило разметки — в `backend/tests/conftest.py`:

| Маркер | Что проверяет | Команда из `backend/` |
|---|---|---|
| `unit` | домен, сценарии на in-memory хранилищах, слои, OpenAPI, сверка конфига механик с [parameters.md](parameters.md) | `uv run pytest` |
| `integration` | HTTP API и хранилища на PostgreSQL: временная база создаётся и удаляется, контейнер поднимается сам | `uv run pytest -m integration` |
| `simulation` | свойства механик на синтетике: сходимость калибровки, потолок показов, точность теста | `uv run pytest -m simulation` |

Весь набор — `uv run pytest -m ""`. Фронт — `npm run verify` из `frontend/`: 29 проверок правил
проекта, типы, Biome, юнит-тесты Vitest и сборка. Сквозной сценарий защиты и проверка
доступности axe в обеих темах — `npm run e2e` при поднятом стенде с демо-данными и dev-сервере
на `:5180` (`npx vite --port 5180`; другой адрес — `E2E_BASE_URL`).

## Стенд валидации

Синтетические кандидаты с известной истиной проходят те же сценарии теста и калибровки, что
HTTP, на in-memory хранилищах. Команды из `backend/`:

| Команда | Что делает |
|---|---|
| `uv run --group validation python -m validation` | отчёт валидации: D1 и D2 по сидам плана проходят тест, повтор, наивный тест B0 и подборку с двойниками M3 и M5, базовые линии B1–B3 ранжируют те же пулы; вердикт по каждой метрике — в [validation-report.md](validation-report.md), картинки — в `validation-report/`. Тот же прогон — тот же файл байт в байт; полный прогон идёт в пуле процессов десятки минут, `--candidates`, `--pairs`, `--warm`, `--compare`, `--report` — для короткого прогона в другой файл. Группа `validation` — зависимости B2 (эмбеддинги локально), веса модели первый прогон скачивает в кэш Hugging Face. B3 отвечает из кэша `validation/data/recorded/b3.<набор>.json` без сети и ключа API, пара без ответа в кэше — ошибка; в коротком прогоне B3 нет. Первый прогон по плану пишет выборку D4 и форму разметки в `validation/data/d4/` — один раз, начатую разметку не затирает |
| `uv run python -m validation b3` | пары B3 по наборам, сколько уже в кэше, прикидка стоимости живого прогона; `--record N` — спросить модель о парах без ответа в N процессов, у каждого свой каталог конфигурации CLI |
| `uv run python -m validation honesty` | честность погрешности уровня и стабильность грейда на прогретом банке D1 |
| `uv run python -m validation tune` | подбор поправки погрешности `level_sd_inflation` на настроечном наборе D3 |
| `uv run python -m validation fit` | подбор проверки согласия семейства с моделью на D3: пять гипотез на банке с испорченными семействами, около часа |
| `uv run python -m validation parsing` | M21: точность разбора потребности из текста по полям на размеченном наборе D5 |
| `uv run python -m validation market` | синтетический рынок файлами: истина в `truth/`, наблюдаемое в `observed/`, потребности и эталон пар; тот же seed — те же файлы |
| `uv run python -m validation acceptance` | обучение модели принятия: CatBoost на 20 000 пар, около шести минут на CPU; пишет `app/adapter/acceptance_model.cbm` и базовые линии M7, тот же сид — тот же файл модели |

Что меряется, на каких данных и с какими порогами — [план валидации](validation-plan.md).

## Банк заданий

Из `backend/`:

- `uv run python -m bank_report` — отчёт покрытия: доля трассировки по темам против потолка,
  сценарные семейства у middle и senior, ячейки «тема × грейд» без семейств и без описания в
  матрице грейдов; с `--calibration` — сверка сложности с экспертной по калибровке из базы;
- `uv run python -m bank_report matrix` — пересобрать [grade-matrix.md](grade-matrix.md) из
  `config/grade_matrix.yaml`.

## Разработка

Бэкенд локально — база, почта и ФСП ID из compose, код с перезагрузкой:

```bash
docker compose up -d db mailpit keycloak
cd backend
uv sync
uv run alembic upgrade head
uv run python -c 'import main; main.sync_catalog()'
uv run uvicorn --factory main:create_app --reload
```

Фронт локально — `cd frontend && npm install && npm run dev`, http://localhost:3000, запросы
`/api` проксируются на `:8000`. Типы API генерируются из OpenAPI при запущенном бэкенде —
`npm run api:types`. Тексты интерфейса — только словари `src/shared/i18n/locales/{ru,en}`, после
нового словаря — `npm run i18n:sync`. Цвета, шрифты и справочник для PDF-профиля и писем бэкенд
берёт из `backend/app/adapter/brand/`; после правки токенов или справочника на фронте —
`npm run tokens:print`.

Заглушка ФСП — синтетика: персоны тестовых участников в `backend/fsp_stub.py`, после правки
`uv run python fsp_stub.py` из `backend/` перезапишет `keycloak/realm-fsp-id.json` и
`backend/config/fsp_registry.json`. Realm импортируется при первом старте Keycloak; чтобы
перечитать — `docker compose up -d --force-recreate keycloak`.

Проверки перед PR:

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy . && uv run pytest -m ""
cd frontend && npm run verify
```

Куда класть новую сущность, порт, миграцию и ошибку — [образцы в архитектуре](architecture.md#образцы).
