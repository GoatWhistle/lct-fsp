# Состояние подбора, демонстрации и подготовки пилота

Срез на 11 октября 2026: код и артефакты `feat/product-readiness` на коммите `385a6ca`.
Исходная точка — `00d1ff2`. При подготовке этой сводки сверены файлы, код сценариев
и метаданные видео; эксперименты и тесты повторно не запускались.

**Доказанного улучшения качества подбора относительно исходной версии пока нет.**
Сравнение с B1/B2 завершено, несколько вариантов механики проверены и отклонены.
Исправлены сессии, подготовлены демо-инструменты и материалы пилота. Полный браузерный
маршрут и готовность ветки к слиянию ещё требуют подтверждения.

## Результаты подбора

Источник — сохранённый [отчёт валидации](validation-report.md), D1/D2: по 3000 кандидатов
и 100 потребностей. γ = 0,80, κ = 1,15, `test_stop_sd` = 0,40.

| Показатель | Исходно, D1 / D2 | Текущий результат, D1 / D2 | B0 | B1 | B2 |
|---|---|---|---|---|---|
| P@10 полной выдачи | 0,900 / 0,812 | 0,900 / 0,812 | 0,958 / 0,958 | 0,441 / 0,449 | 0,453 / 0,483 |
| P@10 при размещении B1/B2 в наших блоках | не опубликован | см. B1/B2 | не приведён | 0,804 / 0,690 | 0,808 / 0,723 |
| Завышение грейда | 0,018 / 0,067 | 0,018 / 0,067 | 0,137 / 0,154 | неприменимо | неприменимо |
| Занижение грейда | 0,394 / 0,393 | 0,394 / 0,393 | 0,138 / 0,230 | неприменимо | неприменимо |

B0 — простой фиксированный тест, B1 — BM25, B2 — эмбеддинги. B3 — сравнение
с LLM-ранжировщиком — не выполнено: записанных ответов нет. Превосходство над B1/B2
не означает превосходства над всеми базовыми линиями; B0 по P@10 выше нашей выдачи.
Интервалы разностей находятся в M1/M2 отчёта.

B1/B2 были реализованы раньше, но прежний отчёт собирался без группы зависимостей
`validation` и не содержал их результатов. Теперь сравнение включено в сохранённый отчёт.
Внутри одинаковых блоков наша сортировка даёт более высокий P@10, чем B1/B2.
Это наблюдение не объясняет проигрыш B0 на полном пуле.

Вероятность принятия проверяется отдельно: M7 описывает модель принятия на синтетике,
M6 — симуляцию рынка (D1 выполнен, D2 не выполнен). Успех по этим метрикам не заменяет
проверку релевантности и не доказывает качество прогноза на реальных людях.

## Что установлено экспериментами

Подробности — [эксперименты](validation-experiments.md).

- Снижение γ до 0,70 уменьшило занижение грейда, но на D9/D10 ухудшило P@10
  и увеличило завышение. В продукте оставлено γ = 0,80.
- Проверенные варианты порога остановки и κ увеличивали длину теста;
  полезное изменение подбора ими не подтверждено.
- Для сигнала согласия попытки подобран `person_fit_lz = 1,0`, но
  `person_fit_enabled = false`: включение ухудшило стабильность на D12
  и не снизило подъём читеров в проверенных условиях.
- Ослабление ограничения показов сократило тест в разведочном эксперименте.
  Влияние на устойчивость к утечке для этого варианта не измерено; он не внедрён.

D9/D10 и D11/D12 уже просмотрены и использованы для решения о внедрении.
Для независимой проверки следующего варианта нужен заранее зафиксированный новый набор.

**Причина проигрыша B0 на полном пуле пока не установлена.** Разбор состава топ-10
выполнен на D1 с 200 кандидатами на специализацию. Там P@10 нашей выдачи 0,855,
B0 — 0,848: исходный проигрыш не воспроизводится. Значительная доля нерелевантных
мест связана с атакующими персонажами, но этот факт не доказывает, что именно они
объясняют разрыв на полном пуле с 600 кандидатами на специализацию.

Сохранённый `.last-run.json` не содержит списка тестов, логов и SHA сборки, поэтому

Точный состав записей и ограничения сценариев приведены в документе демо.

## Что осталось сделать в текущем этапе

1. **Диагностика полного пула.** На D1 и D2 воспроизвести исходный разрыв с B0,
   разложить нерелевантные места по причинам, а пропущенных релевантных кандидатов —
   по категории и позиции внутри категории. Сверить размер пула, потребности,
   конфигурацию и P@10 с основным отчётом. Критерий: объяснение разрыва опирается
   на тот же эксперимент; неразделённые причины явно обозначены. Данные разведочные.
2. **Полный браузерный маршрут.** На свежих синтетических учётках закончить тест,
   создать потребность, отправить приглашение через UI, принять его и проверить
   контакты до и после согласия для того же кандидата и работодателя. Сохранить
   результаты со ссылкой на commit и сборку. Для видеоподтверждения записать оба контекста.
3. **Ревью и PR.** Проверить итоговый diff, исправить существенные ошибки, выполнить
   необходимые проверки изменённых путей и создать PR с критериями приёмки и остатком.
4. **Решение по механике.** По результатам полного пула подготовить до трёх конкретных
   гипотез с минимальным экспериментом, целевой метрикой и рисками. При внедрении
   нового варианта оценить его на новом заранее зафиксированном наборе. Неудача
   нескольких настроек не доказывает необходимость прокторинга.

Документирование этих пунктов не означает, что сами работы выполнены. Сдача текущего
этапа допускает обоснованный отрицательный исследовательский результат, но цель
«улучшить качество подбора» остаётся недостигнутой, пока улучшение не подтверждено.

## Проверки и воспроизведение

В предыдущей сводке указаны 3480 backend-тестов и исправление шести ранее падавших тестов.
Это сведения предыдущего прогона; при редактуре документа они повторно не проверялись.
Для сдачи нужны фактические результаты на соответствующем commit, а не только команды:

```bash
cd backend
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest -m ""
uv run --group validation python -m validation report
```

Проверки frontend: `npm run verify` из `frontend/`. Команды изолированного запуска
и браузерной записи — в [сценарии демо](demo-script.md). Изменение только документации
не требует повторного полного прогона стенда. Генерируемый отчёт правится через сборщик;
его предположение о причине проигрыша B0 остаётся гипотезой до диагностики полного пула.

## Невыполненные и недоказанные требования качества

В сохранённых результатах не выполнены M2 на D2 (0,734 при пороге 0,75), M10 на D2

Отдельно M6 не выполнен на D2. Прохождение M22 на D2 как статистики не означает
включения сигнала в продукте: он выключен по результатам D11/D12.
Полный перечень, включая ожидающие данных метрики, находится в [отчёте](validation-report.md).

Оценка B3 «около 579 $» взята из предыдущей сводки. В `backend/validation/commands.py`
она рассчитывается по константам: 2,5 символа на токен, два хода на пару, 400 входных
токенов накладных расходов и 60 выходных на ход, стоимость 2/10 $ за миллион токенов.
Это допущения калькулятора, а не проверенный актуальный тариф или счёт. Число пар
и состояние кэша выводит `uv run --group validation python -m validation b3`
из `backend/` без `--record`; перед платным запуском нужны актуальная оценка и разрешение.
